# Codex-페이블 병행 개발 규약

## 1. 진실의 우선순위

충돌하는 정보는 다음 순서로 판정한다.

1. 사용자가 직접 확정한 결정
2. 실행 결과와 인게임 관측
3. 현재 코드와 config
4. `docs/BACKLOG.md`의 검증된 기록
5. `docs/HANDOFF.md`와 설계 문서
6. 에이전트의 추측

문서가 코드보다 오래됐을 수 있고, 코드가 사용자의 결정보다 잘못됐을 수 있다. 추측으로 빈칸을 채우지 않는다.

## 2. 작업 시작 절차

1. `SHARED_MEMORY.md`, `ACTIVE.md`, `HANDOFF.md`, 해당 백로그 항목을 읽는다.
2. `git status --short`와 대상 파일의 현재 diff를 확인한다.
3. `ACTIVE.md`에서 같은 백로그 ID나 파일을 다른 주체가 소유하는지 확인한다.
4. 소유자가 없을 때만 `ACTIVE.md`에 작업을 등록한다.
5. 자신의 로그에 시작 시각, 가설, 대상 파일을 기록한다.

## 3. 파일 소유권

- 한 시점에 한 프로덕션 파일은 한 주체만 수정한다.
- 여러 파일이 원자적으로 함께 바뀌어야 하면 한 주체가 통합을 소유한다.
- Codex는 `CODEX_LOG.md`, 페이블은 `FABLE_LOG.md`만 기록한다.
- 상대 로그는 읽기 전용이다.
- `BACKLOG.md` 상태 변경은 구현과 검증을 끝낸 작업 소유자만 한다.
- 대상 파일에 예상하지 못한 새 변경이 생기면 작업을 멈추고 `ACTIVE.md`에 충돌을 기록한다.

## 4. 금지 사항

- 상대 변경을 되돌리지 않는다.
- `git reset`, `git checkout --`, `git stash`, 임의 커밋을 하지 않는다.
- 서버 기동, RCON, 봇 종료·재기동은 사용자 또는 명시된 조율자 승인 없이 하지 않는다.
- `DISCORD_TOKEN`과 그 밖의 비밀값을 파일이나 로그에 기록하지 않는다.
- config에 없는 이름, 수치, 문파 원형을 임의로 만들지 않는다.
- 감사가 통과했다는 이유만으로 인게임 동작까지 검증됐다고 쓰지 않는다.

## 5. 검증 규약

- 수정 전 실패를 재현하고, 가능하면 감사 자체의 self-test를 먼저 확인한다.
- 수정 후 가장 좁은 테스트와 관련 감사부터 실행한다.
- 백로그를 닫기 전 `python3 tools/backlog_audit.py`를 실행한다.
- 닫힌 항목의 실행 가능한 증거까지 확인할 때는 `python3 tools/backlog_audit.py --run`을 사용한다.
- Java 21 모듈은 `JAVA_HOME=$PWD/run/jdk-21` 계약을 사용한다. Java 17 실패를 코드 실패로 기록하지 않는다.
- 빌드 통과와 Paper 플러그인 `onEnable` 성공을 구분해 기록한다.

## 6. 인수인계 형식

각 주체의 로그 항목은 아래 형식을 사용한다.

```markdown
## YYYY-MM-DD HH:MM - B-NNN - 상태
- 목적:
- 소유 파일:
- 확인한 사실:
- 변경:
- 검증:
- 남은 위험:
- 다음 행동:
```

상태는 `조사`, `진행`, `완료`, `차단` 중 하나다. `완료`는 검증 증거가 있을 때만 사용한다.
