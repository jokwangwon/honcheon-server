## 1. 헌장 §2.3 초안 — 광역 산세와 장소 조성의 분리

다음 문안을 헌장 후보로 제안한다.

### §2.3 광역 지형과 장소 조성의 소유권

1. **광역 산세 단계(range stage)** 는 산맥·분수령·능선·골짜기·광역 고도를 소유한다. 범위 식별자, 월드 세대, 범위 명세 지문을 키로 한 별도 장부에 완료를 기록한다.
2. **장소 조성 단계(place prepare stage)** 는 성지·도시·건축 부지·국소 테라스와 진입 공간만 소유한다. 장소 식별자, 월드 세대, 장소 명세 지문을 키로 한 별도 장부에 완료를 기록한다.
3. 두 단계의 장부는 이름이 같더라도 서로 대체하거나 충돌해서는 안 된다. 같은 식별자에 다른 지문이 들어오면 묵시적으로 덮어쓰지 않고 실행을 거부한다.
4. 장소가 이미 완료된 광역 산세에 속하면 `prepare`는 **등록 범위 보존 모드**로 들어간다. 이때 장소 조성은 광역 산을 다시 `shape`하지 않고 범위 장부가 가리키는 `RangeField`·봉우리 높이·표면을 소비한다.
5. 자연 지형 높이 탐침에 의한 조기 반환은 방어선일 뿐, 광역 산세 완료의 권위 있는 판정이 아니다. 단계 완료 여부는 장부로 판단한다.
6. 실행 순서는 원칙적으로 `광역 건식 산세 → 범위 감사 및 장부 완료 → 장소 prepare(범위 보존) → 종속 산길·수계 → 테라스·건축`이다. 다만 수계가 구조물 기초를 침식할 수 있는 경우 구조물보다 먼저 실행하고, 교량·성문 등 보호 구조는 수계 이후 또는 보호 마스크가 있는 채움 전용 단계에서 실행한다.
7. 범위 단계는 경계 연속성 감사를 통과하기 전 완료로 봉인하지 않는다. 특히 B155의 z=0 급단차가 닫히기 전에는 해당 산맥의 광역 실행을 승인하지 않는다.

### 왜 단순히 들림 72 → 160만 바꾸면 안 되는가

현재 `TerrainForge.shape()`의 자연 표면 탐침은 대략 `cy + 70`부터 아래로 내려간다. 기준면 64, 들림 160인 봉우리를 예로 들면 탐침 시작점이 완성 봉우리 내부가 될 수 있고, 그 지점을 자연 표면으로 오인한다. 그러면 실제 정상 높이와 차이가 커져 조기 반환 조건이 성립하지 않고 두 번째 원뿔을 쌓을 위험이 있다.

따라서 헌장에는 다음 두 가지가 함께 들어가야 한다.

- 화산 광역 산세의 승인된 들림을 160으로 올리는 설정 변경
- 광역 장부 완료 시 장소 `shape` 자체를 생략하는 명시적 보존 경로

72 → 160은 설정 결정이고, 중복 조성을 막는 것은 단계·장부 계약이다. 둘을 같은 문제로 취급하면 안 된다.

### 실행 전 필수 봉쇄

- B155의 북쪽 오프셋 8 부근 z=0 최대 33블록 급단차를 먼저 해소한다.
- `RangeField` 자기시험에 경계 양편의 최대 고도차·기울기 연속성 회귀를 추가한다.
- 장소 `prepare`가 범위 장부 완료 뒤 `shape`를 호출하지 않는 통합시험을 추가한다.
- 동일 ID·다른 지문, 월드 재생성, 범위 완료 전 장소 실행을 각각 거부하는 장부 시험을 추가한다.

## 2. CH13 — 해자 문법과 수계 판단

### 2.1 일반 하천 reach를 재사용하지 않는다

기존 하천 문법은 최소 낙차, 보트 통행, 곡류, 단조 하강을 전제한 선형 reach다. 반면 현 해자는 수면 y=60의 정수위 방어 수계이며, 남서쪽 기존 하천 호와 약 270°의 굴착 호가 만나는 구조다. 의미가 다르므로 `rivers:`에 억지로 넣지 말고 전용 `moats:` 또는 `waterworks:` 문법을 둔다.

최소 계약은 다음과 같다.

- 소유 장소와 중심 참조
- 성벽 반경 참조
- 승인된 폭·바닥·수면 참조값
- 기존 하천과 겹치는 호
- 굴착 호의 순서 있는 시작·끝 연결점
- 성문·교량·취수·배수 보호 구간
- `dig`, `fill`, `audit`의 분리된 단계

여기서 새 반경이나 각도 수치를 임의로 만들지 않는다. CH12에서 승인된 형상과 실제 성벽 도면을 참조한다.

### 2.2 순환의 의미

표면 블록은 y=60으로 정수여도 수계 의미는 가질 수 있다. 위수의 서→동 흐름을 기준으로 굴착 호의 두 끝을 다음처럼 해석한다.

- 상류 끝: 통제된 취수
- 하류 끝: 월류 또는 배수

다만 CH9 좌표와 지형을 대조했을 때 확실한 배수구를 놓을 수 없다면, 억지 순환을 서술하지 않고 **단일 통제 취수의 정수 해자**로 남긴다.

### 2.3 “건식 굴착 후 물” 판정

이 순서는 B141의 기존 물 감지 거부를 피한다는 점에서는 옳다. 그러나 현재 `RiverForge.carve`는 수면 위의 비공기 블록을 자연 표면까지 제거할 수 있어, 완성된 교량이나 성문을 나중에 지울 위험이 있다. 따라서 결론은 **조건부 옳음**이다.

허용되는 구현은 둘 중 하나다.

1. 해자 물 단계가 미리 굴착된 마스크 안에서만 작동하는 채움 전용 동작이고, 교량·성문 보호 마스크를 존중한다.
2. 굴착·물 채움을 먼저 끝내고 교량·성문 구조물을 나중에 놓는다.

일반 하천 `carve`를 완성 구조물 뒤에 그대로 호출하는 방식은 승인하지 않는다.

## 3. CH14 — 옹성·교량 배치안

### 3.1 옹성 형식

- 기본안은 직사각형 옹성이다.
- 외문은 본문과 일직선이 되지 않도록 측면으로 비켜 둔다.
- 방어 효과는 특정 장식보다 꺾인 진입선과 이중 문 사이의 통제 공간에서 나온다.
- 크기 수치는 성문 모듈과 성벽 도면이 확정되기 전 만들지 않는다.

역사 자료에서도 옹성은 사각·반원 등 복수 형식이 확인되고, 외문과 본문을 어긋나게 두는 배치가 핵심으로 설명된다. 고정교와 조교 모두 사례가 있으므로 “모든 문에 조교”를 역사적 필수조건처럼 다루지 않는다.

### 3.2 교량 묶음 제안 — 사용자 승인 대기

| 방위 | 제안 | 이유 |
|---|---|---|
| 남문 | 석교 | 주 통행축과 일상 출입 |
| 서문 또는 남서 육문 | 석교 | 흑수 부두에서 환적된 화물의 육상 진입 |
| 북문 | 조교 | 산악 군사로의 통제 강화 |
| 동문 | 보류 | 2단계 동부 노선이 미결이므로 지금 형식을 고정하지 않음 |

동문이 임시로 필요하면 조교 후보로만 기록하고, 생산 설정에는 넣지 않는다. 취수 시설은 남서 육문 가까이에 둘 수 있으나 동일 개구부를 공유하지 않는다.

## 4. CH15 — 수문의 목적과 통항 여부

### 권고: 급수·수위조절형

현 단계에서는 화물선 통과형 수문이 아니라 급수·수위조절형 수문을 채택한다.

- 위수/흑수 수계의 물은 남서쪽에서 통제 취수한다.
- 화물은 흑수 바깥 부두에서 내리고 남서 육문으로 반입한다.
- 해자는 방어·저수·배수 시설이며 성내 화물 운하로 보지 않는다.

양양 사례는 서남쪽 수계가 해자로 들어오고 통제된 흐름이 동북쪽 한수로 빠지는 도시 수계를 뒷받침한다. 그러나 이것이 화물선이 남서 해자 수문을 지나 성내로 들어갔다는 증거는 아니다. 양양의 역사적 부두는 한강 연안의 수륙 환적 기반으로 이해하는 편이 안전하다.

통항 수문을 원한다면 CH9에서 별도 시설 유형으로 다시 설계해야 한다. 최소한 통과 유효폭·높이, 차단문/철책, 수위차 처리 또는 갑문, 성내 항로와 선회·하역 공간을 증명해야 한다. 현재의 폭 8·수심 3만으로는 화물선 통과를 확정할 수 없다.

## 5. 산길 기계 ③ — 계약 초안

### 5.1 입력

- 산기슭에서 정문까지 순서가 있는 `RangeSpec.trail` 경유점
- 등록된 지형 표식, 도하점, 성문 진입점
- B155가 닫힌 `RangeField` 표면·능선 자료
- 승인된 제약: 최대 경사 1:1, 구역당 방향 전환 최소 2회, 직선 대비 경로계수 1.5, 중간 4구역 통과, 무작위 금지

### 5.2 결정 과정

1. `RangeField` 위에 결정론적 후보 경로를 만든다.
2. 경사·회전·경유점·경로계수 제약을 동시에 만족하는 폴리라인을 고른다.
3. 토공은 길과 어깨 폭 안에만 허용한다.
4. 동·서 +84 후보는 서로 거울상으로 평가한다. 표식과 경유점 비용이 한쪽을 선택한다.
5. 완전 동률이면 현재의 임의 동쪽 기본값을 결정으로 굳히지 않고 사용자 선택 미결로 반환한다.

### 5.3 출력과 소유권

하나의 정규 폴리라인을 생성해 다음 소비자가 모두 공유한다.

- `zoneAt`
- 산길 조성기
- 교량 배치
- 연속성·경사·길이 감사

각 소비자가 별도로 길을 재계산하면 구역 판정과 실제 길이 어긋나므로 허용하지 않는다. 실행 시점은 광역 산세와 B155가 닫힌 뒤, 테라스·건축보다 앞이다.

### 5.4 아직 닫을 수 없는 값

- 모든 능선 규모 0.55는 잠정값이다. 차등값을 새로 만들지 않는다.
- `0.7L / 0.3L` 테이퍼는 잠정 형상 상수이며 연속성 미리보기 뒤 승인한다.
- ±25°는 시험용 경로일 뿐 생산 규칙이 아니다. 생산 굴곡은 경유점·경사·회전 제약에서 나와야 한다.
- 4등분 구역은 상속된 잠정안이다. 명명 경유점과 서사 속도에 맞춘 실제 경계는 사용자 승인이 필요하다.

따라서 ③의 인터페이스는 지금 승인할 수 있지만 수치 질문은 B155와 경유점 좌표 전에는 종결할 수 없다.

## 6. 일류 출행 — 진입 동작과 램프

### 권고

일류와 절정은 **같은 진입 동작과 같은 램프**를 쓴다. 차이는 입력 문법이 아니라 도달 상한과 해금 능력이다.

1. 평화·출행 상태에서 1라운드 동안 연속 질주하면 진입한다. 일반 이단도약은 출행 진입으로 취급하지 않는다.
2. 현재 바닐라 질주 속도에서 해당 경지 상한까지 2라운드 동안 선형 상승한다.
3. 질주가 끊기거나 전투가 시작되면 램프를 취소하고 바닐라 이동으로 복귀한다.
4. 일류는 상한 9m/s이며 수평 연쇄 도약은 잠긴다. 기존 수직 공중도약은 유지한다.
5. 절정은 상한 14m/s이며 수평 연쇄 도약을 해금한다.

숙련에 따른 램프 2→1라운드 단축은 기존 제안으로 남기며, 이 문서에서 묵시 승인하지 않는다.

### 안전 핑과 고갈 처리

- 경고 VFX는 실제 60틱 고갈 상태를 미리 설정하면 안 된다.
- 잔여 풀이 2 이하이면 새 수평 연쇄 도약을 거부한다.
- 실제 고갈 시 수평 속도만 현재 바닐라 이동 상한으로 제한한다.
- 수직 속도, 유예 0, 낙하 피해, 전투 배제 규칙은 그대로 보존한다.
- 공중 1.0초·접지 0.4초는 측정값으로만 유지하고 새 상수로 확대 해석하지 않는다.

설계는 일관되지만, 램프 취소·경고와 실제 고갈 분리·수직 속도 보존은 게임 내 회귀시험이 필요하다.

## 7. B150 — TerrainSeal 독립 검토

### 확인한 것

- 열별 지표면과 지표 위 8칸을 봉인 범위로 잡아 고지대 변형 누락을 보완했다.
- 전후 지표면·buildable 상태를 함께 스냅샷한다.
- 습윤 상태 변화만 있는 잡음은 격리된다.
- 실제 `TerrainSeal` 소스를 최소 Bukkit 스텁과 JDK 17로 독립 컴파일해 자기시험을 실행했다: **통과 17, 실패 0**.

### 남은 위양성

현재 허가된 테라스 판정은 대체로 다음 효과를 추론한다.

- 지표 높이가 바뀜
- 또는 블록은 바뀌고 `buildable: false → true`

하지만 이미 `buildable: true`인 열에서 지표 높이는 그대로 두고 지하 공동이나 내부 블록을 채우면, 블록 지문은 바뀌지만 명시적 테라스 마스크가 없어 허가 여부를 정확히 판별하지 못할 수 있다. 현 자기시험의 동일 높이 테라스 사례는 `false → true`를 사용하므로 이 `true → true` 경우를 증명하지 않는다.

### 요구 보완

- 지표·buildable의 부수 효과로 허가를 추론하지 말고, 열별 `land request / terrain delta` 권한 마스크를 봉인 입력에 포함한다.
- 이미 buildable인 동일 높이 열의 허가된 지하 변경과 무단 지하 변경을 각각 시험한다.
- 실제 월드에서 첫 실행과 두 번째 실행의 지문을 비교한다. 단, 두 실행이 같다는 사실은 멱등성만 증명하며 첫 변경의 정당성은 별도 마스크가 증명해야 한다.

**판정: 조건부 통과.** 고지대와 습윤 잡음 문제는 닫혔으나, 명시적 변경 권한 없이 B150을 완전 종결하지 않는다.

## 8. B151 — 지도 표시/건설/접근 3축 독립 검토

### 통과한 부분

- `hidden`은 오직 Boolean `true`, `player_map`은 오직 Boolean `false`로 읽힌다.
- 비관리자는 숨김 장소를 목록·지도에서 보지 못하고 관리자는 볼 수 있다.
- `map_lint.py` 실자료 실행: 위반 0.
- `map_lint.py --selftest`: **63/63 통과**.

### 차단 결함: 접근 축이 없다

설정에는 `access: always`, `rumor`, `faction`, `hidden`, `gate` 등이 존재하지만 `WorldMap.Place`는 `access`를 보유하지 않고 로더도 이를 읽지 않는다. `/혼천 출행 <id>`는 장소 또는 구역을 찾은 뒤 접근 정책이나 공개 장부를 검사하지 않고 플레이어를 이동시킨다.

결과적으로 현재는 다음 상태다.

- 표시 축: 존재
- 건설 축: 존재
- 접근 축: **부재**

비관리자가 ID를 알면 숨김·소문·세력·관문 조건을 우회할 수 있다. 전역 boolean `hidden`만으로는 플레이어별 발견 상태도 표현할 수 없다.

### 요구 보완

1. `access`를 닫힌 타입으로 파싱하고 알 수 없는 값은 거부한다.
2. 플레이어별 발견·소문·세력·관문 상태를 별도 장부로 둔다.
3. 목록, 지도, 직접 ID 출행, 다른 명령/GUI 진입이 같은 접근 판정기를 호출한다.
4. 직접 ID 우회와 `access` 로더 누락을 자기시험으로 고정한다.
5. 구현 전 임시 정책은 비관리자 직접 ID 출행을 막는 것이 가장 안전하다. 최소한 기계적으로 `always` 또는 이미 공개된 장소만 허용해야 한다.

**판정: 실패.** 세 축이 독립적으로 보존됐다는 주장은 현재 코드와 맞지 않는다.

## 9. RP4 A단 — 본체 없는 Display 모형 독립 검토

### 수식·게임 상태 판정

`Rp4DemoRig`의 다음 수식은 현재 `MobDisplay`의 추종·표현·사망식과 정적으로 일치한다.

- 이동거리 기반 위상
- 기울기, 피격, 충전
- 호흡/상하동, 머리, 꼬리, 다리
- 사망 연출

모형 엔티티는 비영속·태그 기반이며 정상 종료/재시작 정리 경로가 있다. `HuntingGrounds`, 판정, 드롭 로직도 직접 변경하지 않는다.

다만 다음 위험이 남는다.

- 뷰어에게 `showEntity`를 호출하면서 리소스팩 수락 여부를 검사하지 않아 팩 실패·대체 표시 경로를 시험할 수 없다.
- 직접 CommandMap 등록에 명시적 해제가 없어 플러그인 reload에서 명령 잔재·중복 바인딩 위험이 있다.
- 레지스트리 독자는 `interval` 필드를 읽지 않아 생산 모델과 실험 모형의 갱신 간격이 나중에 어긋날 수 있다.

### 성능 척도 판정

현재 `nanoTime`은 주로 단계 Java 콜백과 Bukkit 작업 투입 시간을 재며, 틱별 teleport 수는 대리 지표다. 이것만으로는 다음 비용을 재지 못한다.

- 프로토콜 패킷 바이트·빈도
- 서버 엔티티 추적·직렬화
- 클라이언트 렌더 비용
- Display/ModelEngine 내부 스케줄러 비용

따라서 A/B 판정에는 같은 관전자·같은 이동 스크립트·같은 엔티티 수로 외부 틱 프로파일러, 실제 엔티티 수, 프로토콜 패킷 계수 또는 캡처를 함께 써야 한다. 현 teleport 지표는 보조값으로만 남긴다.

### 빌드 확인 제한

현재 환경은 JDK 17뿐이고 프로젝트는 source release 21을 요구한다. `./gradlew build` 및 관련 Java 컴파일은 `invalid source release: 21`에서 멈췄다. 이는 코드 결함 판정이 아니라 검토 환경 제한이며, Fable 측 JDK 21 빌드 증거를 대체하지 않는다.

**판정: 표현 수식은 통과. 실험 척도와 팩 게이트·reload 생명주기는 조건부 실패.**
