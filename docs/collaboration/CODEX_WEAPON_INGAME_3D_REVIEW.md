# Codex → Fable: 무기 3D 인게임 문제 독립 감사

사용자 인게임 스크린샷 `제목 없음.png`를 직접 보았다. 검 신병의 부피는 분명 존재하지만, 정면 페인트보다 압출 옆면·금색 의장·흑자주 보주가 화면을 지배하여 원래 검 그림과 다른 조립물처럼 보인다.

> 감사 기준: 요청서가 고정한 v11 실물(`sword_sinbyeong.json`: 98원소, FP `[-90,-45,115]`, TP `[-90,-45,145]`)을 사용자 스크린샷의 대상본으로 삼았다. 감사 도중 Fable의 병렬 작업으로 작업 트리의 생성기와 JSON이 계속 갱신되었으므로, 아래에서 **v11 판정**과 **현재 작업중 후보 판정**을 분리한다. 현재 후보는 인게임 합격을 뜻하지 않는다.

## 1. 결론

주원인은 확정할 수 있다.

1. **v11 display Euler 합성 순서가 Minecraft/JOML 규약과 반대였다.** 이것이 정면 그림을 옆으로 눕힌 1차 원인이다.
2. **의장 깊이 3.4와 파편 z 산개 ±2.4~3.8은 2차 원인이다.** 잘못된 카메라 각도에서 이 깊이가 옆면 면적을 폭발적으로 키웠다.
3. **FP 스케일 0.4065는 이번 스크린샷의 주원인이 아니다.** 무기는 화면에서 오히려 크게 보이며, 균일 스케일은 정면/옆면의 비율을 바꾸지 않는다.
4. **라우팅 문제는 아니다.** 시점별 대체 모델이 아니라 같은 honcheon 모델의 display 절만 달라진다.
5. **z-fight나 shade는 주원인이라는 증거가 없다.** 회전 원소의 자기 가림과 계단식 셰이딩은 보조 악화 요인이지만, 스크린샷은 깜박이는 공면보다 정상적으로 렌더된 큰 옆면을 보여 준다.

따라서 처방 순서는 **회전만 고친 대조본 → 깊이 위계 축소 → 손 크기 보정**이어야 한다. 세 변수를 한 번에 바꾸면 다음 사용자 판정에서 어느 수정이 맞았는지 다시 알 수 없다.

## 2. 증거별 판독

### 사용자 스크린샷

스크린샷에서 확인되는 것은 다음과 같다.

- 좌측의 옥백 날 일부는 식별되므로 텍스처 누락이나 모델 라우팅 실패가 아니다.
- 화면 중앙의 금색/뼈백 의장과 흑자주 보주가 큰 블록 덩어리로 보인다.
- 정면 몽타주의 검 실루엣을 정의하던 넓은 페인트 면은 좁게 눕고, 그 대신 가장자리 UV가 늘어난 옆면이 연속해서 보인다.
- 파편과 벌어진 의장이 화면 깊이 방향에서 서로 겹치며, 정면에서는 분리되어야 할 음영 공간이 조립 블록의 중첩으로 바뀐다.
- 무기 전체는 화면 하단을 넓게 점유한다. “너무 작아서 3D가 안 보인다”는 그림이 아니다.

사용자의 “입체는 있고 다 좋아보이는데 이미지에 맞는 입체가 아니다”라는 표현이 정확하다. 기하의 존재 여부가 아니라 **정면 설계와 투영된 기하의 대응 관계**가 깨진 상태다.

### 실물 JSON

요청서가 기록한 v11 수치는 실제 볼륨을 증명한다.

- z 범위 3.80~11.80, 총 8.00.
- 깊이 0.7~3.4의 여러 단면.
- y축 회전 원소 48개.

따라서 “평판이라서 문제”라는 진단은 기각한다. 다만 총 깊이 8은 정면 높이 약 10 안팎인 검 의장에 비해 매우 크다. 특히 날 능선 1.7에 대해 의장 3.4는 두 배이고, 파편 중심은 본체에서 최대 3.8 떨어진다. 카메라가 조금만 옆으로 가도 의장 옆면과 파편 간 거리의 투영이 정면 그림보다 강해진다.

## 3. Minecraft 1.21.11 display 의미론

### 회전 순서

Minecraft의 item transform 경로가 사용하는 JOML `Quaternionf.rotationXYZ(x,y,z)`는 다음 쿼터니언을 만든다.

```text
R_MC(x,y,z) = Rx(x) · Ry(y) · Rz(z)
```

열벡터에는 오른쪽 항부터 닿으므로 실제 점은 **Z → Y → X** 순으로 돈다. 로컬 JOML 1.10.8 jar의 `rotationXYZ` 바이트코드를 직접 확인했고, 공식 JOML API도 `rotationX(x).rotateY(y).rotateZ(z)`와 동치라고 명시한다.

참조: <https://joml-ci.github.io/JOML/apidocs/org/joml/Quaternionf.html#rotationXYZ(float,float,float)>

현재 `core.py`에 남아 있는 옛 `_euler_to_mat()` 주석과 구현은 반대로 `Rz·Ry·Rx`를 “MC 규약”이라고 적는다. 현재 `_display()`는 더 이상 이 헬퍼를 쓰지 않지만, 그대로 두면 다음 리팩터링에서 같은 버그를 재도입한다. 헬퍼를 실제 규약으로 고치거나 이름을 `_legacy_euler_to_mat`로 바꾸고 사용 금지를 명시해야 한다.

### translation·rotation·scale

item display는 포즈 행렬에 개념적으로 `T · R · S`를 쌓는다. 열벡터 관점에서 정점에는 scale, rotation, translation 순으로 적용된다.

이번 문제에서는 이것이 별도 원인이 아니다.

- scale은 세 축이 같은 균일값이므로 회전과 교환 가능하고 면 각도를 바꾸지 않는다.
- translation은 위치만 바꾸고 방향벡터·법선에는 영향을 주지 않는다.
- 잘못된 것은 T/R/S의 큰 순서가 아니라 **R 내부의 Euler 축 순서**다.

## 4. 1인칭 행렬을 손으로 푼 판정

### 바닐라 기준

바닐라 `item/handheld`의 오른손 1인칭 회전은 다음이다.

```text
B_fp = R_MC(0, -90, 25)
```

우리 무기는 길이축이 모델 +X이고, 바닐라 스프라이트는 XY 평면에서 +45° 대각선이다. 따라서 모델을 로컬 Z로 먼저 +45° 돌린 후 바닐라 회전을 적용해야 한다.

```text
P = Rz(45)
R_intended = B_fp · P
           = Rx(0) · Ry(-90) · Rz(25) · Rz(45)
           = R_MC(0, -90, 70)
```

즉 오른손 1인칭의 정확한 JSON 값은 **`[0,-90,70]`**이다. 행렬을 역산할 필요도 없고 z 슬롯에 45를 더하면 된다.

왼손은 선회전을 거울로 바꾸므로 **`[0,90,-70]`**이다.

### v11 값이 만든 오차

v11은 잘못된 `Rz·Ry·Rx` 규약으로 합성·역산하여 오른손에 `[-90,-45,115]`를 썼다. Minecraft가 이것을 실제 규약으로 해석하면 다음과 같다.

```text
R_v11 = Rx(-90) · Ry(-45) · Rz(115)
```

모델의 정면 페인트 법선 `n=(0,0,1)`을 비교하면:

```text
바닐라/정답: R(0,-90,70) · n       = (-1, 0, 0)
v11:          R(-90,-45,115) · n   = (-√1/2, +√1/2, 0)
```

두 법선의 각도는 정확히 **45°**다. v11은 바닐라 검과 같은 면을 보여 준 것이 아니라 정면을 45° 비틀어 옆면 쪽으로 눕혔다. 이후 손/카메라 변환이 무엇이든 두 모델 사이의 상대 45° 오차는 그대로 남는다.

행렬 원소 최대 절대오차도 v11은 약 1.36인 반면 `[0,-90,70]`은 부동소수 오차 약 `1.1e-16`으로 의도 행렬과 일치한다.

### 3인칭

같은 계산으로 오른손 3인칭은 다음이다.

```text
B_tp = R_MC(0, -90, 55)
B_tp · Rz(45) = R_MC(0, -90, 100)
```

- 오른손: `[0,-90,100]`
- 왼손: `[0,90,-100]`

v11의 `[-90,-45,145]`도 정면 법선을 바닐라 기준에서 똑같이 45° 틀며, 의도 행렬과의 원소 최대 오차는 약 1.80이다.

## 5. 네 용의자 판정

| 용의자 | 판정 | 근거 | 처방 |
|---|---|---|---|
| 1. display 과축소 | **이번 FP 증상의 주원인 아님; 3인칭 크기에는 별도 영향** | 균일 스케일은 면 비율을 바꾸지 않으며 스크린샷에서 무기는 작지 않다 | 회전 수정 뒤 본체 기준 스케일을 별도 조정 |
| 2. display 면 방향 | **맞다 — 주원인** | v11 정면 법선이 바닐라 기준에서 정확히 45° 이탈 | 우 FP `[0,-90,70]`, 우 TP `[0,-90,100]`; 왼손은 부호 반전 |
| 3. 합성 순서 | **맞다 — 근본 원인** | 옛 헬퍼 `Rz·Ry·Rx`와 JOML `Rx·Ry·Rz`가 반대 | z 슬롯 직접 가산 또는 올바른 행렬 헬퍼 사용 |
| 4. 회전 원소 셰이딩/z-fight | **보조 악화 가능, 주원인 아님** | 스크린샷은 공면 깜박임보다 큰 옆면과 자기 가림을 보임 | 깊이·z 산개 축소, 면-ID 검수; z-fight는 별도 움직임 영상으로 확인 |

## 6. 스케일 처방

v11 FP scale은 다음 계산이다.

```text
0.68 × (22 / 약 36.8) = 0.4065
```

공통 프레임 36.8에는 본체뿐 아니라 수실·방사 파편까지 포함된다. 이 때문에 실제 손에 쥐는 검 몸체가 불필요하게 축소되는 진단 자체는 맞다. 다만 이것은 “이미지와 다른 입체”의 원인이 아니라 **가독성을 추가로 낮춘 별도 문제**다.

권장 분리는 다음과 같다.

- GUI: 전체 프레임 extent를 유지한다. 모든 파편이 슬롯 안에 있어야 한다.
- 1인칭/3인칭: 날+의장+자루의 **본체 extent**를 사용한다.
- 수실과 부유 파편은 hand/fp 분모에서 제외한다.
- 검의 잠정 상한은 FP 24, TP 30이 합리적인 시험 범위다. 현재 작업중 JSON의 FP 약 0.49, TP 약 0.77은 바닐라 0.68/0.85보다 여전히 작아 폭주한 수치는 아니다.

다만 현재 작업중 `_body_extent()`처럼 “깊이 ≤0.9면 부유물”로 분류하면 안 된다. 얇은 필리그리·깃·천도 0.7~0.9일 수 있으나 본체에 붙은 구조다. 깊이는 역할이 아니다.

```text
role = body | attached | float
```

- `body`: 날, 자루, 코등이, 소켓, 보주.
- `attached`: 필리그리, 깃, 고리, 수실 매듭. 본체 scale에는 선택적으로 포함.
- `float`: 비접촉 파편과 멀리 떨어진 기운만 제외.

shape의 깊이 태그에 역할을 함께 기록해 bbox를 계산해야 이후 깊이 튜닝이 display 크기를 우연히 바꾸지 않는다.

## 7. “이미지에 맞는 입체”를 위한 깊이 처방

### 현재 문제

v11의 구조는 기술적으로 복셀 3D지만, 큰 정면 셰이프에 하나의 깊이를 부여해 압출하는 방식이 남아 있다. 특히 `_VD_ORN=3.4`가 소켓 띠·브래킷·코등이처럼 성격이 다른 부품을 한 깊이로 묶는다.

“실제 블록으로 구성됨”은 모든 장식을 깊게 압출한다는 뜻이 아니다. 정면 그림의 부품마다 알맞은 단면을 가져야 한다는 뜻이다.

### 권장 단면

| 부위 | 권장 총 깊이 | 형상 문법 |
|---|---:|---|
| 날 인선 | 0.55~0.75 | 가장 얇은 바깥 1셀 |
| 날 사면 | 1.0~1.25 | 인선에서 능선으로 한 단 상승 |
| 날 능선 | 1.4~1.7 | 현행 상한 유지 가능 |
| 자루 | XY 폭과 같은 1.2~1.6 | 정사각/팔각 봉 근사 |
| 얇은 필리그리·깃 | 0.7~1.1 | 얇은 봉/판을 ±22.5°로 벌림 |
| 구조 코등이·소켓 | 1.8~2.2 | 날보다 두껍되 폭 전체를 3.4로 만들지 않음 |
| 보주 | 1.7~2.4 | XY 지름과 비슷한 입방/구 근사 |
| 상감 | 숙주보다 한 면당 0.25~0.45 돌출 | 절대 깊이보다 숙주 기준 상대값 |
| 수실 | 0.5~0.7 | 앞/뒤 오프셋은 ±0.4~0.7 |
| 부유 파편 | 0.6~0.9 | 중심 z 오프셋은 우선 ±0.8~1.6 |

구체적으로 `_VD_ORN=3.4` 하나를 다음처럼 쪼갠다.

```text
VD_FILIGREE = 0.9
VD_GUARD    = 2.0
VD_COLLAR   = 1.6~1.9
VD_BOSS     = 2.2~2.6
```

검 신병의 앞 반고리 브래킷과 금 소켓 띠는 3.4가 아니라 1.4~1.9가 적합하다. 현재 날 능선 1.7보다 약간 두꺼운 정도면 구조적으로 충분하다.

### z 산개

`_SHARD_POSE=((2.4,...),(-2.8,...),(3.4,...),(-3.8,...),...)`는 총 z 범위를 8까지 키운 직접 원인이다. 정면에서 고리 둘레에 배치한 파편이 1인칭에서는 의장 앞뒤로 깊게 흩어져 다른 구도를 만든다.

1차 시험값:

```text
z = (+0.8, -1.0, +1.4, -1.6, +1.1)
angle = (+22.5, -22.5, +22.5, -22.5, +45)
```

- 45° 파편은 한 개만 남긴다.
- 파편은 정면 XY 위치가 주연이고 z는 겹침 방지용 보조여야 한다.
- 회전 수정 후에도 파편이 보주나 날을 가리면 z를 더 늘리지 말고 XY 방사 위치를 옮긴다.

## 8. 회전 원소·shade·z-fight

### shade

Minecraft 블록 모델의 면 음영은 연속적인 PBR 조명이 아니다. 회전된 사선면도 제한된 방향·baked quad 셰이딩으로 양자화되어, ±22.5°와 ±45° 원소가 기대보다 같은 밝기 또는 급격히 다른 밝기로 보일 수 있다.

이는 얇은 필리그리가 블록처럼 보이는 원인이 될 수 있지만, 넓은 페인트 면 자체가 사라진 원인은 아니다. 정면 각도를 먼저 고쳐야 한다.

처방:

- 핵심 날과 보주는 `shade` 기본값으로 입체감을 유지한다.
- 얇은 발광 파편·옥빛 기운은 필요할 때만 `shade:false` A/B를 시험한다.
- 모든 원소에 일괄 `shade:false`를 쓰면 볼륨이 다시 평면 스티커처럼 된다.

### z-fight와 자기 교차

복셀러는 픽셀마다 최종 승자 shape 하나를 고르고 같은 태그 영역을 병합하므로, 회전되지 않은 기본 타일 사이에 넓은 공면 중복을 일부러 만들지는 않는다. y회전 뒤 인접 복셀이 서로 관통할 가능성은 있으나, 이는 대개 z-fight보다 **자기 가림·교차 덩어리**로 보인다.

정지 스크린샷에는 z-fight를 입증하는 깜박임 정보가 없다. 회전하며 촬영한 영상에서 무늬가 떨릴 때만 공면 문제로 분류한다.

예방값:

- 의도적으로 겹친 두 판의 면 간격은 최소 0.03~0.05 모델 단위.
- 같은 평면의 장식은 별도 box를 포개지 말고 한 텍스처/한 shape로 합성.
- 회전 원소의 origin과 숙주 bbox를 감사해 회전 후 교차 체적이 숙주 체적의 15~20%를 넘지 않게 한다.

## 9. 현재 병렬 수정 후보 판정

감사 중 관측한 현재 작업 트리에는 다음 변화가 있었다.

- FP 오른손 `[0,-90,70]`, 왼손 `[0,90,-70]`.
- TP 기본 후보 `[0,-90,100]`/`[0,90,-100]`.
- 본체 extent 분리와 FP 24/TP 30 상한.
- 3인칭에 길이축 180° 롤을 더한 최종 후보: 오른손 `[180,90,-100]`, 왼손 `[180,-90,100]`.
- 감사 시점 생성 JSON은 FP 약 0.4908, TP 약 0.7669였고 z 전체 범위는 여전히 3.8~11.8이었다.

판정:

1. **z 슬롯 직접 가산은 승인한다.** 의도 행렬과 수치적으로 정확히 같다.
2. **본체 extent 분리는 방향상 승인한다.** 다만 깊이 문턱이 아니라 역할 태그로 바꿔야 한다.
3. **3인칭 180° 롤의 행렬은 맞다.** 

   ```text
   R_MC(180,90,-100) = R_MC(0,-90,100) · Rx(180)
   ```

   길이축 +X는 유지하면서 정면/뒷면과 인선 방향 Y를 뒤집는다. 도의 날이 앞뒤 반대였다는 별도 실측에는 유효한 처방이다.
4. 단, 180° 롤을 모든 계열에 일괄 적용하면 창 홍영·권갑 엄지·겸/구 갈고리처럼 위아래 비대칭인 계열도 뒤집힌다. 9계열 좌/우 3인칭 시트를 확인한 뒤 공통 계약으로 확정하거나 계열별 `hand_roll`을 둬야 한다.
5. **회전 수리는 깊이 과장을 자동으로 해결하지 않는다.** z 산개 8과 범용 의장 3.4는 별도 축소가 필요하다.

## 10. 반드시 분리해서 만들 대조 팩

### A — 원인 확정본

- v11 기하·텍스처·스케일 그대로.
- display 회전만 직접 z 가산 값으로 변경.

합격: 같은 FOV의 1인칭에서 검의 정면 페인트가 즉시 식별되고, 스크린샷 중앙의 옆면 덩어리가 크게 줄어든다.

### B — 깊이 교정본

- A + 의장 깊이 역할 분리.
- 파편 z 오프셋을 ±0.8~1.6으로 축소.

합격: 정면 아트의 고리·보주·깃 배치가 1인칭에서도 같은 순서와 겹침 관계로 보인다. 옆면은 입체를 증명하되 정면보다 넓지 않다.

### C — 크기 교정본

- B + 본체 extent 기준 FP/TP 스케일.

합격: 검은 바닐라 손 검의 약 70~90% 존재감을 가지며 화면 중앙을 과도하게 막지 않는다. 장병기는 별도 상한으로 감쇄된다.

세 장을 같은 좌표·같은 FOV·같은 배경에서 찍어야 한다. A가 실패하면 깊이나 스케일을 더 만지지 말고 display/손 변환 재현부터 다시 본다.

## 11. 권장 검수 장치

### 6면 ID 디버그 모델

한 자루만 검수용으로 다음 단색을 입힌다.

- north/south: 흰색/검정.
- east/west: 빨강/파랑.
- up/down: 초록/노랑.

1인칭 우·좌, 3인칭 전·후를 찍으면 어느 면이 카메라를 보는지 추측 없이 확정된다. 생산 팔레트 감사와 분리된 임시 검수 자산이어야 한다.

### 행렬 자기시험

생성기 자기시험에 다음을 고정한다.

```text
R(display_fp_right) == R(vanilla_fp_right) · Rz(+45)
R(display_fp_left)  == R(vanilla_fp_left)  · Rz(-45)
R(display_tp_right) == R(vanilla_tp_right) · Rz(+45)
```

행렬 원소 최대 오차 `≤1e-6`을 요구한다. JSON 각도 문자열 비교만으로는 동치 Euler 표현을 놓칠 수 있으므로 반드시 행렬로 잰다.

### 시각 합격 기준

- 정면 페인트 면이 보이는 픽셀 면적의 최소 65~70%를 차지한다.
- 옆면은 15~25% 범위에서 두께를 설명하고 주 실루엣을 덮지 않는다.
- 보주·코등이·날의 앞뒤 순서가 GUI와 1인칭에서 동일하다.
- 검을 좌우로 천천히 돌릴 때 공면 깜박임이 없다.
- 3인칭 오른손/왼손에서 도·겸·구의 인선 방향과 권갑 엄지 방향이 의도와 맞는다.

## 12. 최종 답

- **기하는 진짜 3D인가?** 맞다.
- **왜 이미지에 맞지 않았나?** v11이 Minecraft의 Euler 순서를 반대로 해석해 정면 법선을 45° 틀었고, 3.4 깊이 의장과 최대 ±3.8 파편이 그 오차를 큰 옆면 덩어리로 증폭했다.
- **스케일이 원인인가?** 이번 1인칭 스크린샷의 원인은 아니다. 다만 파편 포함 프레임으로 손 크기를 재는 방식은 별도로 고쳐야 한다.
- **정확한 1인칭 값은?** 우 `[0,-90,70]`, 좌 `[0,90,-70]`.
- **정확한 기본 3인칭 값은?** 우 `[0,-90,100]`, 좌 `[0,90,-100]`.
- **현재 Fable 회전 수정은 맞나?** z 슬롯 직접 가산은 맞다. 3인칭 180° 롤도 행렬상 맞지만, 전 계열 비대칭 방향을 확인해야 한다.
- **다음 배포는?** 회전만 바꾼 A를 먼저 사용자에게 보여 원인을 닫고, 그다음 깊이 B, 마지막으로 크기 C를 적용해야 한다.
