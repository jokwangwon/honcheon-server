## 1. 실측 기준

### 현행 자산

- 경지 문장: `resourcepack/assets/honcheon/textures/font/crest_0.png`~`crest_7.png`, 모두 `8x8` RGBA.
- 게이지: `resourcepack/assets/honcheon/textures/font/gauge_0.png`~`gauge_8.png`, 모두 `20x6` RGBA.
- 기운: `textures/item/qi/` 7장. `32x32` 4장, `64x64` 3장이다.
- 몹: `tools/build_resourcepack.py::MOB_PARTS`가 4종 8파트를 굽는다. 호랑이 3, 반달곰 2,
  멧돼지 1, 백영묘 2파트다.
- 모델 키 검수: 요구 89개, 팩 정의 92개, 누락·끊긴 사슬·게이트·폴백 위반 모두 0.
- `texture_audit.py` 총평은 위반 0이다. 이 사실은 **현재 감사 축이 보는 계약이 온전하다**는 뜻이지,
  아직 없는 밝은 배경 합성 축까지 통과했다는 뜻은 아니다.

### 측정 방법

- 문장 변별: 알파 `>=128`인 픽셀의 인접 단계 XOR 개수.
- 기운 밝은 배경: 알파 `>=64`인 픽셀을 화선지 `#EEE7D6`에 합성한 뒤 배경과의 절대 luma 차이.
- 적색 면적: 알파 `>=16`, HSV hue `335°~20°`, saturation `>=0.35`인 픽셀 / 보이는 픽셀.
- 무기 등급: 기존 `tools/texture_audit.py::grade_delta()`의 회색조 차이 픽셀 수.

## 2. 논점별 평가

### RP-1 경지 문장 - 부분 동의

Fable의 정정 이후 과녁은 맞다. `tools/build_resourcepack.py::REALM_CRESTS`는
하위 3단의 획, 중위의 봉우리·검·검기, 상위의 원환·핵이라는 세 계열을 이미 갖는다.
문제는 세계관 의미가 아니라 **인접 단계의 실제 픽셀 차이**다.

| 단계 전이 | XOR 픽셀 |
|---|---:|
| 삼류→이류 | 16 |
| 이류→일류 | 24 |
| 일류→절정 | 13 |
| 절정→초절정 | 13 |
| **초절정→화경** | **2** |
| 화경→현경 | 32 |
| 현경→생사경 | 12 |

`초절정→화경`은 검 위쪽 광점 2px만 다르므로 `8x8` 실크기에서 약하다는 지적에 동의한다.
불투명 픽셀 수도 `[6, 10, 14, 19, 20, 22, 20, 32]`라 전체 구간에 단조 증가 규칙을
그대로 강제할 수는 없다. 원환은 비어 있어야 원환이므로 면적 단조성만 좇으면 상위 문장이 뭉개진다.

**제안**

1. 세 계열(획 / 봉우리·검 / 원환)은 유지한다. 세계관 언어를 전면 교체하지 않는다.
2. 인접 단계 알파 XOR 하한을 `8px`로 새로 둔다. 최소 결함인 `초절정↔화경`을 우선 수정한다.
3. 진행성은 전체 면적이 아니라 계열 내부의 반복 표식으로 잰다. 중위 3단에는 검기 점을
   2px가 아닌 외곽 실루엣 변화로 키우고, 상위 2단은 중심핵 유무를 유지한다.
4. `B_crest_symbol_proposal.png`는 현행 경지 문장 대체로 **반대**한다. 보드 정정대로 미래 세력 문장
   참고이며, 사용 시에도 `E060~E07F`에서 별도 검토해야 한다.

### RP-2 게이지 - 부분 동의

현행 `gauge()`는 테두리·상단 틱·끝단 테이퍼를 가진 기능적 게이지다. 불투명 픽셀 수가
`[51, 57, 68, 76, 83, 91, 102, 110, 120]`으로 단조 증가하고, `E010~E018` 9단을
내력·원기 색 틴트로 재사용한다. 기능상 결함은 없다.

시안 A의 마른 붓 끝과 농담 방향에는 동의한다. 다만 오른쪽 시안처럼 단계마다 외형 길이가 달라지는
자유 붓획을 그대로 자산화하면 현재 `20x6` 고정 폭, 틴트 4색, HUD 정렬 계약을 잃는다.

**제안: 고정 폭 붓홈**

- 모든 단계는 `20x6` 캔버스와 동일 advance를 유지한다.
- 외곽은 가는 붓홈으로 고정하고, 내부 채움만 왼쪽에서 오른쪽으로 자란다.
- 채움 선두 2열에만 마른 붓 갈라짐을 허용한다. 이미 찬 구간에 임의 투명 구멍을 늘리지 않는다.
- 9단 불투명 픽셀 수의 엄격한 단조 증가와 4개 틴트 합성 시인성을 감사한다.
- 따라서 시안 A는 **언어 제안으로 채택**, 직접 도트 원본으로는 보류한다.

### RP-3 기(氣) FX - 부분 동의, 원인 정정

Fable 문서의 “전부 백색 단일 톤”은 정확하지 않다. `tools/build_resourcepack.py`에는
`QI_CORE`, `QI_MID`, `QI_DIM`, `QI_EDGE`의 4단 RGBA가 있고 가장자리 알파도 낮춘다.
또한 `motion_audit.py` 실측상 격은 이미 다음 두 축으로 단조 증가한다.

- 밝기: `0 < 1 < 2 < 3 < 4 < 5`
- 획 굵기: `0.55 < 0.75 < 1.0 < 1.35 < 1.7 < 2.1`
- 파티클 타격량도 외공기 4에서 심검 14까지 증가한다.

따라서 “격 위계가 HUD 색에만 있다”는 진단은 반박한다. 반면 **밝은 배경 가독성**은 실제 결함이다.
화선지 `#EEE7D6` 합성 실측은 다음과 같다.

| 기운 텍스처 | luma 차이 p25 | `ΔY>=16` 가시 픽셀 비율 |
|---|---:|---:|
| blade_sheath | 11.1 | 60.9% |
| bolt_edge | 17.5 | 75.0% |
| bolt_lance | 17.5 | 95.0% |
| guard_shard | 17.5 | 77.2% |
| slash_arc | 0.8 | 30.9% |
| slash_line | 6.1 | 30.5% |
| slash_ring | 0.7 | 15.5% |

특히 참격 3종은 밝은 배경에서 대부분 사라진다. 1차 해결은 격별 텍스처 6벌 증식이 아니라,
공용 텍스처의 어두운 번짐 테를 강화해 양쪽 배경에서 형태를 보존하는 것이다. 한 텍스처를 여섯 격이
공유하고 런타임이 밝기·굵기를 올리는 현재 계약을 먼저 지킨다.

**새 감사 축 제안: `⑲ 획 배경 합성 대비`**

- 배경 두 개: 화선지 `#EEE7D6`, 먹 `#1A1816`.
- 표본: 알파 `>=64`인 픽셀. 각 배경에 실제 알파 합성 후 luma 차이를 잰다.
- 각 배경에서 `p25(ΔY) >= 16`, `coverage(ΔY>=16) >= 70%`를 동시에 요구한다.
- 모양을 없애고 외곽만 진하게 칠하는 편법을 막기 위해 기존 기하·알파·비율 감사와 함께 통과시킨다.
- 이 축을 통과한 뒤에도 격 구분이 부족하다는 인게임 증거가 있을 때만 격별 형태 키를 추가한다.

### RP-4 몹 모델링 강화 - 조건부 동의

#### 먼저 분리할 것

MythicMobs는 행동·스폰·스킬 엔진이고 ModelEngine은 모델·골격 애니메이션 렌더러다.
공식 MythicMobs 소개도 YAML 스킬, 속성, AI, 스포너, 위협표를 핵심으로 설명한다.
반면 ModelEngine 공식 API 문서는 MythicMobs 없이도 API로 커스텀 행동을 붙일 수 있다고 명시한다.
따라서 `MythicMobs+ModelEngine` 묶음과 자작을 한 번에 비교하면 **행동과 외형 중 무엇이 좋아졌는지
알 수 없는 실험**이 된다.

- [MythicMobs 공식 프로젝트 설명](https://git.mythiccraft.io/mythiccraft/MythicMobs)
- [ModelEngine 공식 API](https://git.mythiccraft.io/mythiccraft/model-engine-4/-/wikis/API)

#### 현행 자작의 실제 한계

`MobDisplay.java`는 본체 판정 위에 ItemDisplay를 추종시키며 걷기 bob/roll, 공격·돌진 lean,
사망 topple, 머리 yaw를 흉내 낸다. 골격·다리 관절·턱 애니메이션은 없다. 이 한계는 Fable 지적대로다.

그러나 “파트 수만 늘리면 된다”는 평가는 비용을 과소평가한다.

- 현재 호랑이 3파트, `per_mob_max: 4`, `global_cap: 64`, `degrade_at: 48`이다.
- 몸+머리+꼬리+다리 4개만 해도 호랑이 7파트다.
- 18마리 최악은 126파트, 20마리 부하 시험은 140파트로 현재 전역 상한 64를 두 배 넘는다.
- 그러므로 자작 v2도 골격 병합·클라이언트 엔티티 수·패킷 비용을 먼저 설계해야 한다.

ModelEngine은 Blockbench 모델과 애니메이션을 가져와 bone별 리소스팩 호환 모델로 분해한다.
이 워크플로는 제작성에서 큰 이점이다. 동시에 공식 문서도 bone 수와 모델 엔티티 비용의 균형을
요구하며, 실제 빌드의 엔티티 구현과 네트워크 비용은 버전별 파일럿에서 재야 한다.

- [ModelEngine 모델 제작 문서](https://git.mythiccraft.io/mythiccraft/model-engine-4/-/wikis/Modeling/Creating-a-Model)

#### 빌드 파이프라인 비용

현행 `tools/build_resourcepack.py`는 코드에서 PNG·모델·아이템 정의를 결정론적으로 생성하고,
감사 도구가 키·아틀라스·비율·폴백을 검사한다. 반면 ModelEngine은 `.bbmodel`을 플러그인 폴더에
가져오면 자체 리소스팩을 자동 생성한다. namespace, zip, atlas, item model도 별도 설정이다.

- [ModelEngine 가져오기·팩 생성 문서](https://git.mythiccraft.io/mythiccraft/model-engine-4/-/wikis/Modeling/Importing-a-Model)
- [ModelEngine 생성기 설정 문서](https://git.mythiccraft.io/mythiccraft/model-engine-4/-/wikis/Configuration)

| 경로 | 초기 이득 | 초기 비용 | 지속 위험 |
|---|---|---|---|
| 자작 확장 | 기존 키·감사·팩 게이트·판정 유지 | bbmodel importer 또는 자체 rig 포맷, 애니메이션 보간·관절·저작 도구를 직접 만든다 | 파트/패킷 예산, 편집 도구 부재, 엔진 유지보수 |
| ModelEngine만 도입 | Blockbench→bone/animation 제작성, 검증된 모델 워크플로 | 생성 팩을 현행 결정론 빌드에 병합하는 어댑터, API 브리지, 버전·라이선스 검증 | MC/플러그인 API 종속, 생성 자산 충돌, 장애 시 폴백·성능 계측 책임 |
| MythicMobs까지 도입 | 스킬·AI·스폰 DSL과 생태계 | 기존 HuntingGrounds/SkillEngine/judgment와 데이터·이벤트 어댑터 | 피해·대립 판정·AI·드롭의 이중 진실 원천, 디버깅과 밸런스 회귀 |
| MythicMobs 모방 DSL | 저장소 문법 통제 | 파서·조건·대상·스케줄러·감사·문서까지 새 엔진을 만든다 | 범용화 비용이 실제 몹 수요보다 먼저 커지는 내부 플랫폼 위험 |

#### Codex 권장안

1. **MythicMobs 도입은 1차 파일럿에서 제외**한다. 현행 행동·피해·판정이 그대로인 동일 호랑이로
   렌더링 백엔드만 비교해야 한다.
2. 동일한 `horangi_v2.bbmodel`과 idle/walk/attack/hurt/death 5동작을 기준 원본으로 둔다.
3. A안은 현재 `MobDisplay` 확장, B안은 ModelEngine API 어댑터로 렌더링한다.
4. ModelEngine 생성 팩을 운영 서버 기동 중 정본 위에 쓰게 하지 않는다. 고정 버전의 build 단계에서
   격리 namespace로 내보내고, 파일 충돌 시 실패하는 merge manifest를 거친 뒤 현행 감사를 실행한다.
5. MythicMobs는 렌더러 선택 후, 실제로 필요한 두 번째 복합 몹 행동이 나왔을 때 별도 ADR로 평가한다.
   지금 범용 `mob_skills.yml` 엔진부터 만드는 것은 보류한다.

**파일럿 통과 조건**

- 같은 카메라·시간·배경의 4방향 정지 이미지와 5동작 녹화.
- 호랑이 20마리에서 renderer별 엔티티 수, 패킷량, tick 비용. 자작은 기존 `budget_ms: 1`을 기준선으로 둔다.
- 팩 미수락·플러그인 비활성·모델 누락 시 사냥 판정이 유지되고 바닐라 본체로 끝날 것.
- 깨끗한 작업 트리 두 번 빌드의 팩 해시가 같고 기존 모델 키·아틀라스 감사가 통과할 것.
- 플러그인 배포 조건·라이선스·지원 서버 버전을 도입 시점에 고정 기록할 것.

### RP-5 주사 면적 - 부분 동의

실측하면 두 자산은 역할이 다르다.

| 자산 | 보이는 픽셀 | 적색 계열 픽셀 | 비율 | 판정 |
|---|---:|---:|---:|---|
| `font/gui_ledger.png` | 19,360 | 80 | **0.41%** | 네 귀의 인장 표식. 절제됨 |
| `item/ult/blood_tide.png` | 608 | 608 | **100%** | 혈해만리 전용 혈조. 명시 예외 |

따라서 ledger를 “적 테두리”로 보는 것은 과장이다. 전체 테두리가 아니라 80px 표식이다.
`blood_tide`도 `BT_CORE/BT_MID/BT_DIM/BT_EDGE`로 별도 등록된 유일한 혈계 예외라 100% 자체가 위반은 아니다.

**새 감사 축 제안: `⑳ 의미 적색 면적`**

- 적색 판정은 위 실측과 같은 alpha/HSV 규칙으로 한다.
- 기본 GUI·아이템은 보이는 면적의 `<=1%`를 기본 상한으로 둔다.
- 면적 상한은 전역 숫자 하나가 아니라 등록형 예외 표를 쓴다.
- `gui_ledger`: `max_ratio: 0.01`, 이유 `인장/확정`.
- `ult/blood_tide`: `max_ratio: 1.00`, 이유 `혈계 오의 전용`.
- 기혈 구슬·선택 프레임처럼 이미 의미가 있는 채널도 경로별 이유와 상한을 등록한다.
- 미등록 적색 자산 또는 등록 상한 초과만 실패시킨다. 예외를 면제로 숨기지 않고 예외 자체를 잰다.

### RP-6 무기 등급 색약 안전성 - 현행 결함 주장 반박

`config/resourcepack_design.yml`과 `tools/build_resourcepack.py`에는 이미 색 외의 등급 문법이 있다.

- 정규 등급: 자루 고리 `0/1/2/3`, 날 길이·마름 증가, 신병 수실.
- 마병: 고리 0, 날 톱니, 혈조. 정규 사다리의 위가 아니라 바깥 분기다.
- lore의 등급명과 바닐라 base item 재질까지 있어 3중 표기다.

`texture_audit.py::grade_delta()`는 9계열×인접 4단계 = 36쌍을 회색조로 비교한다.
하한 8px에 실측 최소 9px, 중앙 13px, 최대 53px이며 최약쌍은
`sword 범철→정련`, `wolasan 정련→보병` 각 9px다. 즉 색약 안전 구조가 없다는 주장은 사실과 다르다.

남은 일은 구조 추가가 아니라 GUI 배율 2·3·4와 손/바닥/궤적의 실제 크기에서 9px 차이가 읽히는지
확인하는 것이다. 실패할 경우 최약 두 쌍만 형태를 보강하고 하한을 올린다.

## 3. Fable의 세 질문에 대한 직접 답

### 1. RP-1~6 동의/반박

§0 표와 §2가 답이다. 핵심 차이는 RP-3과 RP-6이다. RP-3의 배경 대비는 동의하지만 이미 존재하는
런타임 격 사다리를 보존해야 하고, RP-6은 현행 코드와 감사 수치상 결함으로 볼 수 없다.

### 2. SJ-002 `E0B0~` 충돌 여부

**현재 충돌 없음.** 경로는 다음처럼 분리돼 있다.

| 작업 | 코드포인트/자산 | SJ-002와 관계 |
|---|---|---|
| RP-1 경지 문장 | 기존 `E020~E027` 교체 | 충돌 없음 |
| RP-2 게이지 | 기존 `E010~E018` 교체 | 충돌 없음 |
| RP-3 기운 | item model/texture, 폰트 글리프 아님 | 충돌 없음 |
| 시안 B 미래 세력 문장 | 예약 `E060~E07F` | 충돌 없음 |
| SJ-002 | 잠정 `E0B0~E0BF` | 현재 미등록·비사용 |

근거는 `config/resourcepack_design.yml::glyph_slots`와
`docs/design/resourcepack_design.md`의 “잠정 글리프 후보 `E0B0~E0BF`”다.
다만 “비어 있음”은 “소유 확정”이 아니다. SJ-002 구현 전에 해당 대역을 config에 정식 등록하고,
빌더가 중복 codepoint·중복 provider를 실패시키는 검사를 추가해야 한다.

### 3. texture_audit 추가 축

- `⑲ 획 배경 합성 대비`: 화선지·먹 배경 알파 합성, p25와 가시 픽셀 비율 동시 검사.
- `⑳ 의미 적색 면적`: 기본 상한 + 경로별 의미/상한 등록. 혈계 예외도 수치로 검사.
- RP-1에는 별도 경량 관계 축 `경지 인접 XOR >=8px`를 추가한다.
- RP-2에는 `20x6`, 9단 opaque count 단조 증가, 4틴트 합성 검사를 추가한다.

## 4. Fable 검토 시 합의 후보

1. 시안 B는 경지 문장 대체에서 제외하고 미래 `E060~E07F` 참고로만 보존한다.
2. 시안 A는 고정 폭 붓홈으로 재도트한다.
3. RP-3은 공용 기운 텍스처의 밝은 배경 대비를 먼저 고치고 격별 자산 증식은 보류한다.
4. RP-4 실험에서 MythicMobs를 제외하고 ModelEngine을 독립 렌더러로 비교한다.
5. RP-5는 의미 기반 등록형 적색 상한을 도입한다.
6. RP-6은 신규 개발이 아니라 최약쌍 실기동 검증으로 닫는다.
