# 모델 엔진 도입 — BetterModel (2026-07-20)

## 왜

사용자 결정: **"여러 종 그리고 몹들도 엄청 많이 생성할 예정입니다 필요하다 판단 넘어가죠"**

앞선 물음은 이것이었다 — *"무협 세상이다 보니 보스가 사람이지만 막 우락부락한데
공격하는 모션인 손 들기 등 한다면 그걸 세세하게 표현 가능한지"*.

**현재 `MobDisplay` 로는 안 된다.** 실측:

| | |
|---|---|
| config 에 등록된 역할 | `body`(5) · `leg`(4) · `tail`(3) · `head`(3) — **`arm` 이 없다** |
| 코드가 아는 역할 | `head` · `leg` · `tail` **셋뿐** |
| 공격 모션 | 다리 회전 **한 줄**이 전부 (`attackRaiseDeg` — 덮치는 짐승의 앞발) |
| 등록된 몹 | horangi · bandal_gom · baegyeongmyo · metdwaeji — **전부 네발짐승** |

`arm` 역할을 더하고 손으로 짜는 길도 있었지만, **종이 여럿이고 개체가 많다**는 전제에서는
모션 하나하나를 코드로 쓰는 비용이 종 수만큼 곱해진다. 저작 도구가 필요하다.

★ **MythicMobs 는 답이 아니다** — 그쪽은 스킬·AI 스크립팅이지 모델/애니메이션 엔진이 아니다.
넣으면 전투 판정이 우리 `npcStrike` 와 저쪽으로 **갈라진다**.

## 실측 (테스트 서버)

**★ Java 25 가 필요하다.** BetterModel 3.x 는 class 69 로 컴파일돼 있어 우리 JDK 21(class 65)에서
`UnsupportedClassVersionError` 로 죽는다. 2.2.0 은 class 65 라 21 에서 돌지만 옛 판이다.
→ **테스트 서버만** `run/jdk-25` 로 올렸다. **라이브는 JDK 21 그대로다.**

기동: `Done (47.9s)` · **오류 0건** · HoncheonMVT 1.0.0 + MagicSpells 4.0-B18 + BetterModel 3.3.0 **공존**

### 동봉 모델 `demon_knight` 의 뼈대 — 물음에 대한 직접 답

`hammer_attack_1/2/3` `shield_attack_1/2` — **인간형 무기 공격 모션이 이미 있다.**

## 하네스에 붙인 것

- `--bm-model <모델>` — BetterModel 형체를 세우고 찍는다
- `--bm-anim <애니메이션>` — 촬영 중 주기적으로 재생 (한 번 재생하고 끝나므로 다시 건다)

**두 함정을 코드에 박아 뒀다:**

1. **`bm spawn` 은 콘솔에서 안 된다** (자리가 없어 인자 파싱이 거부된다). 대신 봇을 **변장**시킨다.
   첫 판에서 spawn 이 실패했는데 하네스가 **직전 판의 호랑이를 붙잡아** "팔이 돈다"를 냈다
   (`foe_id = horangi · 파츠 7개`). 그래서 이제 세울 때 고아 파츠까지 **먼저 지운다.**

2. **파츠 수를 세지 않는다.** BetterModel 3.x 는 표시 엔티티를 **패킷으로** 보낸다 —
   월드에 실물이 없으니 `@e` 로는 원리상 0 이다. **여기서 파츠 0 은 고장이 아니다.**
   이 갈래의 유일한 증인은 화면이다.

### 검사기 두 곳을 고쳤다

- `vfx_preflight.py` 의 팩 사슬이 **라이브 경로를 못 박아** 읽고 있었다. 테스트가 제 팩을 쓰게 된
  뒤로 그건 **엉뚱한 파일과 견주는 눈**이 됐다 — 서버가 잰 값과 봇에게 보낸 값이 서로 맞는데도
  "서버가 옛 팩을 잰다"고 외쳤다. 이제 `resource_pack.yml` 의 `local_path` 에서 읽는다.
- `frame_motion()` 에 **얼어붙은 화면** 판정을 넣었다. Xvfb :98 의 프레임버퍼가 굳어
  171프레임이 **바이트까지 동일**했는데 하네스는 그것을 "정지"로 적었다.
  0px 는 「안 움직인다」가 아니라 **「못 봤다」**일 수 있다 — 이제 그렇게 말한다.

## 카메라 「죽은 화면」 — 짚었고, 피하게 만들었다 (2026-07-20 추가)

**증상:** 연무장에서 `--angle front` 만 141프레임이 **바이트까지 동일**했다. `side` 는 멀쩡했다.

**아니었던 것들** (하나씩 재서 지웠다):
- 클라가 죽은 것 — 아니다. F1 을 보내면 HUD 가 6,048px 토글된다 (키가 닿고 클라는 산다)
- 캡처가 낡은 화면을 긁는 것 — 아니다. F1 토글 전후로 **35,474px** 이 바뀐다 (캡처는 살아 있다)
- 청크 렌더가 굳은 것 — F3+A 로 안 풀린다
- 블록에 가린 것 — 카메라와 표적 사이 다섯 칸이 전부 공기다
- 엔티티에 가린 것 — 주변엔 플레이어 둘뿐
- 구름 — `cloudStatus:0` · `graphicsMode:"fast"` 로 꺼도 같다
- **BetterModel** — 변장을 풀어도 **똑같이 깨진다**
- 차원·자리 착오 — F3 가 `honcheon_dojang` · `XYZ 0.5/-60/5.9` 라고 말한다

**정체:** **자리에 매인 llvmpipe 렌더 오류.** 표적 앞 5.4칸(z=5.9) 그 자리에서만
반투명 판이 시야를 덮고 바닥이 황토빛으로 물들며, 그 그림이 완전히 정지한다.
거리별 실측 (2초 사이 변화):

| 거리 | 2.0칸 | 3.0칸 | **5.4칸** | 7.5칸 |
|---|---|---|---|---|
| 변화 | 19,607px | 15,391px | **0px** | 1,483px |

3.0칸에서는 정면 전신이 **완벽하게** 나온다(뿔 투구·갑옷·망토·보석까지).
Mesa `25.2.8` / `llvmpipe (LLVM 20.1.2)` — **우리가 못 고치는 층**이다.

**고친 방식: 원인을 못 고치니 그 자리를 피한다.**
`camera_alive()` 를 촬영 **앞**에 둔다 — 두 장을 사이 두고 긁어 같으면 죽은 눈이다.
죽었으면 거리를 0.62배·1.35배로 흔들어 다시 세운다. 실측으로 확인:
`화면이 죽었다 → 0.56배도 죽었다 → 1.22배에서 눈이 살아났다` → front 0px 이 **1,872px** 이 됐다.

★ 8초를 찍고 나서 「죽은 화면이었다」를 아는 건 늦다. 그래서 **찍기 전에** 묻는다.

## 남은 것

- **변장은 바닐라 몸을 다 못 가린다** — 형체 안으로 플레이어의 몸통·다리가 비쳐 보인다.
  변장(`bm disguise`) 갈래의 문제이고, 실제 몹은 `spawn` 을 지나므로 다를 수 있다. 확인 필요.
- 특정 공격 애니메이션을 **명령으로 꽂는 길**은 아직 없다. `/bm test` 는 제 인스턴스를 따로
  세워 거기서 재생한다. 실제로는 우리 플러그인이 **API 로** 거는 것이 맞는 길이다.
- 본서버 도입은 **별개 결정**이다. 라이브가 JDK 25 로 올라가야 하고, 그건 따로 판단할 일이다.
- 기존 `MobDisplay`(936줄)와의 관계 — 대체할지 공존할지 정해야 한다.
  네발짐승 4종은 이미 그것으로 돌고 있다.
