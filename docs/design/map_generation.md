# AI 기반 마인크래프트 맵 생성 파이프라인

> 전제: 블록을 손으로 쌓지 않는다. AI로 맵을 생성한다.
> 핵심 원칙: **맵은 그리는 것이 아니라 컴파일하는 것이다.**
> `config/regions/*.yml`(장소·연결·사건)이 이미 존재하는 지역의 논리 구조다 —
> 맵 생성기는 이 데이터를 입력으로 받아 공간으로 변환한다.
> 맵 스펙: `config/map_spec/*.yml`

---

## 1. 원칙 — 단일 진실 원천에서 컴파일

```text
config/regions/cheongha_hyeon.yml   ← 지역의 논리 (장소, NPC, 사건, 연결)
config/map_spec/cheongha_hyeon_map.yml ← 지역의 공간 (지형, 구역, 도로, 규모)
          ↓ 맵 컴파일러 (tools/mapgen/)
월드 파일 + 게임 데이터 바인딩 (NPC 앵커, 트리거 존, 스폰 규칙)
```

장점:
- **재생성 가능**: 시드 + 스펙 → 언제든 동일/개선된 맵 리빌드. 스펙은 git으로 버전 관리, 월드 파일은 빌드 산출물.
- **논리-공간 정합 보장**: 청하객잔이 config에 있으면 맵에 반드시 존재하고, NPC 한백의 앵커가 그 안에 박힌다. 손 빌드에서 생기는 "설정과 맵의 어긋남"이 원천 차단.
- **지역 확장 = 스펙 추가**: 사천 당가세력권 스텁이 승격될 때, 맵 작업은 스펙 작성부터 시작.

## 2. 4계층 파이프라인

```text
L1 지형(Terrain):   섬서 외곽의 산세·강·평지 — 하이트맵 기반
L2 구조물(Structure): 객잔·관아·성벽·민가 — 파라메트릭 건물 생성기
L3 배치(Layout):    현성 구획, 도로망, 장소 간 거리 — 배치 문법 + region 데이터
L4 바인딩(Binding):  NPC 앵커, 사건 트리거 존, 소문 브로드캐스트 존, 스폰 규칙
```

## 3. 도구 선택지와 권장 조합

| 계층 | 도구 후보 | 권장 |
|------|-----------|------|
| L1 지형 | WorldPainter(헤드리스 스크립트 지원), 커스텀 노이즈 생성 → amulet로 기록 | **WorldPainter 스크립트** — 하이트맵 PNG 입력, 성숙한 도구 |
| L2 구조물 | amulet-core(파이썬 월드 편집), GDPC(GDMC HTTP 모드 — 절차 생성 연구 표준), WorldEdit/FAWE 스키매틱, 구조물 블록 NBT | **파이썬 파라메트릭 생성기(amulet 또는 GDPC)** — 스키매틱 라이브러리를 코드가 생산 |
| L3 배치 | 커스텀 배치기 (region YAML + map_spec 읽어 좌표 결정) | **자체 컴파일러** — 이 프로젝트 고유 로직 |
| L4 바인딩 | 플러그인이 읽을 JSON/YAML 산출 (좌표 ↔ location_id 매핑) | 컴파일러가 함께 출력 |

## 4. AI의 역할 분담 — 무엇을 AI가 하는가

```text
LLM (Claude)이 하는 일:
  1. 맵 스펙 작성       — 지역 설정 → 공간 스펙 (구역, 규모, 분위기, 배치 제약)
  2. 생성기 코드 작성    — 파라메트릭 건물 생성기 (객잔 생성기, 성벽 생성기, 민가 문법)
  3. 배치 문법 설계      — "관아는 중심, 폐사당은 외곽 숲, 나루는 강변" 같은 제약 규칙화
  4. 반복 개선          — 렌더/스크린샷 검토 → 스펙·생성기 수정 (사람은 방향만 지시)

이미지 생성 AI (선택):
  하이트맵/컨셉 — "섬서 외곽, 북쪽 산길이 지나는 산자락과 강" → 하이트맵 초안
  (노이즈 함수 조합만으로도 충분할 수 있음 — 비용 대비 검토)

절차적 코드가 하는 일 (결정론):
  실제 블록 배치 전부. AI는 블록을 직접 놓지 않는다 —
  같은 스펙+시드는 항상 같은 맵. 디버그 가능, 부분 리빌드 가능.
```

핵심: **"AI로 맵 생성" = AI가 생성 시스템을 만들고 운영하는 것**이지, 프롬프트 한 번에 월드가 나오는 마법이 아니다. 대신 이 방식은 지역이 늘수록 한계비용이 급감한다 (두 번째 현부터는 스펙 작성이 일의 대부분).

## 5. 맵 스펙 스키마 (초안)

```yaml
map_spec:
  region_ref: 지역 config 경로        # 논리 원천
  seed: 고정 시드
  scale: 블록 규모 (현성 지름, 외곽 반경)
  terrain: { 기반 지형, 하이트맵 소스, 강/산 배치 제약 }
  districts: 구역들 (성내/장터/외곽/산길/강변) — 각 구역에 location 소속
  roads: 도로망 (장소 간 연결 = region의 이동 동선)
  locations: location_id별 { 구역, 건물 생성기, 파라미터, 상대 배치 제약 }
  bindings: { npc_anchors, trigger_zones, broadcast_zones, spawn_rules }
```

청하현 실물 초안: `config/map_spec/cheongha_hyeon_map.yml`

## 6. 게임 데이터 바인딩 — 맵이 시스템과 만나는 곳

컴파일러가 월드와 함께 좌표 매핑을 출력하면, 플러그인(core 엔진)이 이를 읽는다:

```text
NPC 앵커:        한백 → 청하객잔 1층 계산대 좌표 + 동선(2층 계단 흘끗거림)
트리거 존:       폐사당 반경 = 기연 조건 카운터(방문 3회), 창고 뒷문 = 조사 상호작용
소문 브로드캐스트 존: 객잔 홀 = inn_net 대사 풀 재생 구역
지역 상태 체감:   치안↓ → north_road 구역의 도적 스폰율 테이블
사건 무대:       north_road 매복 지점 = 습격 이벤트 스폰 좌표
```

## 7. 로드맵

```text
M0. 맵 스펙 스키마 확정 + 청하현 스펙 v0 ✅
M1. 건물 생성기 1종 프로토타입 — 객잔 ✅ (tools/mapgen/inn_generator.py —
    스펙 파라미터 구동, 결정론 검증, ASCII 평면도 + L4 바인딩 출력.
    MC 월드 기록 어댑터는 M2에서)
M2. L1 지형 + L3 배치기 — 청하현 지형에 구역·도로·건물 배치
M3. L4 바인딩 출력 + 플러그인 소비 검증 (NPC 앵커에 한백이 서 있는가)
M4. 렌더 검토 루프 (스크린샷 → 스펙 수정) → 청하현 v1
M5. 두 번째 지역으로 한계비용 검증 (스펙만 새로 쓰고 생성기 재사용)
```

## 8. 리스크

```text
- 절차 생성의 균질함: 규칙으로 만든 마을은 티가 난다 → 생성기에 변주 파라미터
  (비대칭, 낡음 정도, 증축 흔적) + 랜드마크(폐사당, 성황당)는 개별 생성기로 정성 제작.
- 무협/동양 건축 문법: 바닐라 블록으로 기와·처마 표현 — 초기 생성기 개발에 미적 반복 필요.
  (리소스팩 커스텀 블록은 차후 옵션)
- 도구 의존성: amulet/GDPC의 MC 버전 추종 — 컴파일러는 도구 추상화 계층을 얇게 유지.
```
