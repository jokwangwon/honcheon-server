# 시스템 점검 — 왜 숫자는 좋아지는데 눈에는 나빠졌나 (2026-08-11)

사용자 지시: 「기존 기능이 있다면 <b>바로 사용하는 게 아닌</b> 해당 기능이나 시스템을
확인하고 분석하고 개선하거나 새로 생성하는 방식으로 진행하고…
<b>눈의 문제가 자주 보이므로</b> 개선책을 제시하고 판단하여 개선」

## 있는 것 · 상태

| 시스템 | 하는 일 | 상태 |
|---|---|---|
| `config/blueprints/*.yml` | 좌표 정본 | **건강** — 하루에 층·소품·팔레트를 다 받아냈다 |

| `screen_metric.py` 등 화면 자 | 색 분포 | **★위험** — 오늘 벽돌 기둥에 최고점을 줬다 |

## ★눈이 실패하는 세 가지 유형

지금까지 자를 <b>스무 번 넘게</b> 고쳤다. 사유를 모아 보니 셋뿐이다.

1. **오늘의 값을 외운 자** — 「깊이−13」·「37×18」·좌표 `(7,8)`.
   도면 치수가 바뀌면 죽는다. → <b>규칙을 물어라</b>. (고치는 법 확립됨)
2. **이름으로 구조를 고르는 자** — `contains("mangrove_log")`.
   팔레트가 바뀌면 죽는다. → <b>구조를 물어라</b>. (확립됨 · `shaftIndex`)
3. **★색만 재는 자** — 평균 명도 · 어두운 면 비율 · 최빈색.
   <b>「무엇으로 읽히는가」를 못 잰다.</b> ← 오늘의 실패. **아직 답이 없었다.**

3번이 위험한 까닭: 1·2번은 <b>헛짖는다</b>(조성은 멀쩡한데 자가 운다). 3번은 <b>안 짖는다</b> —
잘못 만든 것에 최고점을 준다. 오늘 `red_nether_bricks` 기둥이 색 지표 만점이었고 실물은
조적 기둥이었다.

## 고친 것 ① — 색표를 <b>손에서 뺐다</b>

`blueprint_draw.py` 는 <b>손으로 적은 17종</b> 표를 갖고 있었다. 팔레트가 바뀌어도
안 따라 적으면 아무도 안 죽으니 조용히 낡았다 — 재 보니 64%를 모르고 있었다.

→ `tools/block_palette.py`: 클라이언트 jar 의 <b>실제 텍스처</b>에서 뽑는다.
리소스팩이 덮은 블록은 <b>팩 것을 쓴다</b>(게임에서 보이는 것이 그것이다).

```
블록 색표 1110종 (팩이 덮은 것 236종) · 본전이 쓰는 재료 13종을 <b>전부</b> 안다
```

- 선형(sRGB→linear) 평균 — 감마 공간에서 평균 내면 어두운 텍스처가 밝게 나온다
- 알파 128 미만은 색이 아니다 (살창의 빈 곳)
- 불투명 비율을 함께 낸다 (성긴 것을 도면이 알아야 한다)
- <b>모르는 재료는 자홍색으로 칠하고 이름을 세어 보고한다</b> — 조용히 안 넘어간다
- 눈의 눈 10개 (선형 평균 검증 포함) — `--selftest`

## ★남은 구멍 — 도면이 실물의 <b>절반</b>만 그린다

색표를 물리고 다시 그리니 정면도·측면도가 제대로 나온다. 그런데 <b>지붕이 없다.</b>
도면은 `plan`+`columns` 만 그리고, <b>지붕·공포·간포·처마·소품은 조성기가 만든다</b> —
그래서 도면에 안 보인다. 실루엣의 절반이 지붕인데.

<b>그래서 이 도면으로는 오늘의 문제를 못 잡았을 것이다.</b>

## ③ 완료 — 읽힘 자 (2026-08-11)

### 무엇을 재나 — <b>결</b>

색만 재는 자는 「무엇으로 읽히는가」를 <b>영영 못 잡는다</b>. 색 분포가 같아도 무늬가 다르기 때문이다.
그래서 <b>변화의 방향</b>을 잰다. 텍스처는 타일링되므로 가장자리는 감싸서 잇는다.

```
Ex = 가로로 갈 때의 변화량  →  <b>세로선</b>이 만든다 (나무결·세로살)
Ey = 세로로 갈 때의 변화량  →  <b>가로선</b>이 만든다 (벽돌 줄눈·단 이음)

방향 = (Ex−Ey)/(Ex+Ey) ∈ [−1,+1]     + 세로결 · − 가로줄눈
세기 = (Ex+Ey)/2/255                  0 이면 민판
```

★<b>세기를 먼저 본다.</b> 무늬가 약하면 방향은 뜻이 없다 —
`red_terracotta` 는 방향이 −0.184 지만 세기가 0.007 이라 <b>민판</b>이다.
이걸 「가로줄눈」이라 부르면 자가 헛짖는다.

★이것은 <b>재료의 성질</b>이라 사진도 카메라도 필요 없다. 눈이 즉석에서 부른다.

### 자를 검증했다 — 세 갈래가 깨끗이 갈린다

```
통나무 옆면   oak +0.422 · dark_oak +0.416 · spruce +0.432 · birch +0.424 · cherry +0.469
             stripped_oak +0.307 · stripped_dark_oak +0.295        → 8종 중 <b>6종 세로결</b>
조적         bricks −0.197 · stone_bricks −0.207 · red_nether_bricks −0.321
             nether_bricks −0.318 · mud_bricks −0.191 · blackstone −0.163  → <b>7종 전부 가로줄눈</b>
민판         red_terracotta 0.007 · white_concrete 0.003 · polished_andesite 0.009
```

예외 둘(`mangrove_log` −0.390 · `stripped_mangrove_log` −0.210)은 <b>자가 맞다</b> —
그 텍스처가 실제로 가로 띠다. (우리가 오래 쓰던 기둥 재료도 그랬다는 뜻이다.)

### 박은 눈 다섯

```
★★★적주가 <b>조적으로 안 읽힌다</b>           (red_terracotta = 민판 → 통과)
★★[눈의 눈] red_nether_bricks 는 잡힌다
★★[눈의 눈] 통나무는 안 잡힌다 (헛짖지 않는다)
★★살창에 <b>결이 있다</b>                     (dark_oak_trapdoor 세기 0.0351)
★★공포와 창방이 <b>명도로 갈린다</b>           (114.5 대 74.2 · 차 40)
```

### ★끝까지 확인했다

도면에 `red_nether_bricks` 를 실제로 넣고 눈을 돌렸다:

```
✗ ★★★적주가 조적으로 안 읽힌다 (red_nether_bricks = 가로줄눈)   → 507/508
되돌린 뒤                                                    → 508/508
```

<b>어제의 실패를 오늘의 눈이 짓기 전에 잡는다.</b>

### 아직 못 재는 것 (정직하게)

- <b>「와플처럼 보인다」</b> — 격자의 <b>주기</b>가 굵어 촌스러운 것은 방향이 0 이라 「격자」로만 읽힌다.
  주기(공간 주파수)를 재면 되지만 이번엔 안 넣었다
- <b>배치의 읽힘</b> — 「공포가 통짜 판으로 뭉친다」는 재료가 아니라 <b>이웃과의 관계</b>다.
  명도 차 자를 하나 넣었지만 이건 시작일 뿐이다
- <b>그늘</b> — 실제 화면의 어두움은 재료 명도가 아니라 빛이 만든다. 그건 사진의 몫이다

## ④ 완료 — 사진 → 치수 (2026-08-11)

지금까지 레퍼런스에서 뽑아 쓴 것은 <b>색</b>뿐이었다. 치수는 내가 눈으로 세어
「정면 7칸쯤」 하고 말했다 — 그래서 도면과 나란히 놓고 따질 수가 없었다.

`tools/ref_measure.py` 는 <b>선</b>을 찾는다. 목조 정면은 기둥과 수평 부재가 만드는
격자이므로, 그 격자를 찾으면 칸 수·칸 폭의 비가 <b>수로</b> 나온다.

```
세로선 = 각 x 에서 가로 방향 변화를 <b>세로로 합한다</b> (길게 이어질수록 커진다)
가로선 = 축만 바꿔 같은 것
```

### 첫 판이 두 곳에서 무너졌고, 둘 다 진짜였다

1. **민판에서 헛선을 만들었다** — 평평한 그림은 평균도 표준편차도 0 이라
   「평균+0.55σ 이상」을 <b>모든 화소가</b> 통과한다.
   → 절대 바닥(`LINE_FLOOR`): 선을 따라 쌓인 변화가 <b>길이당 2.0</b> 에 못 미치면 선이 아니다.
2. **굵은 기둥 하나를 둘로 셌다** — 좌·우 두 모서리. 최소 간격만으로는 부재가 그보다
   굵을 때 못 막는다.
   → 뒤에 한 번 더 묶는다: <b>가장 넓은 칸의 0.4 배</b>보다 좁게 붙은 봉우리는 한 부재다.
   (부재 폭 &lt; 칸 폭 은 목조 건축에서 언제나 참이다.)
   ※<b>홀로 선 부재 하나</b>는 원리적으로 못 가른다 — 견줄 칸이 없다. 문서에 적었다.

### ★첫 실측 — 우리 정면은 레퍼런스의 <b>절반 밀도</b>다

```
[사진] 09_honjeon 상자 (450,415,985,515)
  세로선 14개 → <b>13칸</b> · 어칸:협칸 = <b>1.65</b>
[도면] hwasan_honjeon
  기둥열  8개 → <b>7칸</b>  · 어칸:협칸 = <b>1.25</b>
```

★고지: 사진의 14 는 <b>모든 세로 부재</b>다 — 구조 기둥과 <b>문틀</b>이 섞여 있다.
그러므로 「레퍼런스가 13칸짜리 건물이다」가 아니라 <b>「세로 부재의 밀도가 우리의 두 배다」</b>가
옳은 읽기다. 그리고 그 밀도가 곧 「우리 정면이 2.4배 거칠다」의 정체다.

어칸의 상대 폭도 다르다 — 레퍼런스 1.65 대 우리 1.25. <b>레퍼런스의 중앙이 더 넓다.</b>

```

쌓임(간선)   적주 = [기단, 기단, 주초, <b>몸통</b>, 창방, 도리, 긴보]
             창호 = [기단×3, <b>살창</b>, 회벽, 창방, 도리, 긴보]
기법         툇간 · 민면 · 다포 · 주심포 · 겹처마
위계         본전 [툇간·다포·겹처마] → 강당 [툇간·주심포] → 창고 [민면·주심포]
```

★<b>켜 수는 푼다</b>. `fill` 인 부재가 <b>남는 켜를 먹는다</b> — 「높이 12」를 주면
몸통 켜가 스스로 정해진다. 사람이 세지 않는다.

★같은 재료가 <b>두 노릇</b>을 하면 부재를 둘로 적는다 (회벽 = 창 위의 가는 띠 ·
회벽면 = 칸을 채우는 면). 안 그러면 한 쌓임에 채움이 없어 <b>못 푼다</b> — 사전이 스스로 짖는다.

### 무엇이 주석에서 <b>구조</b>가 되었나

| 전 | 후 |
|---|---|
| 「창방·도리·긴보는 모든 칸의 끝 세 켜」 (주석) | 사전이 그렇게 적혀 있으므로 <b>어길 수가 없다</b> |
| 「높이는 모든 칸이 같다」 (사람이 셈) | 채움이 남는 켜를 먹으므로 <b>언제나</b> 맞는다 |
| 「격이 낮으면 덜어 쓴다」 (말) | `ranks` 가 기법 목록을 준다 — <b>새 기법을 못 만든다</b> |


### 눈 아홉 — 그중 셋이 <b>계약</b>이다

```
★모든 칸이 같은 높이다              ★수평 부재가 한 높이에서 이어진다
★높이가 모자라면 거기서 죽는다        ★격이 낮으면 기법이 준다 · 창고는 툇간이 없다
★어칸이 협칸보다 넓다               ★사전의 끝 두 켜가 손으로 쓴 본전과 같다
```

★자를 또 한 번 고쳤다: 「끝 세 켜가 같다」를 <b>항목 문자열</b>로 쟀더니, 같은 재료가
이웃하면 한 항목으로 합쳐져(`mangrove_planks*2`) 칸마다 항목 수가 달라 짖었다.
조성은 멀쩡한데 자가 <b>대용품</b>을 잰 것이다 — 켜로 펴서 고쳤다.
(이 저장소에서 <b>스물몇 번째</b> 같은 병이다. 유형 ①②③ 중 ②의 변종이다.)

## ②-b 3D 를 <b>빡세게</b> — 실제 블록 형태로 (2026-08-11 · 사용자)

> 「반블럭 계단블럭을 포함한 <b>명확한 표현</b>이 되어야 하고, 위치나 블럭을 명확히 하여
>   3d에서 빡세게 잡고 가야 함」

첫 판은 모든 블록을 <b>정육면체</b>로 그렸다. 그래서
· 반블록으로 만든 도리가 <b>통짜 보</b>로 보였고
· 계단으로 짠 공포·처마·지붕이 <b>네모 덩어리</b>가 됐고
· 트랩도어 살창이 <b>꽉 찬 벽</b>이 됐다
— <b>우리가 형태로 만든 것을 형태 없이</b> 그렸다. 그러면 3D 로 볼 이유가 없다.

### ① 덤프가 <b>블록 상태</b>까지 적는다

```
전  x,y,z,block                 deepslate_tile_slab
후  x⇥y⇥z⇥data                  minecraft:deepslate_tile_slab[type=bottom,waterlogged=false]
```

상태 문자열에 쉼표가 들어가므로 <b>탭</b>으로 가른다 (`.csv` → `.tsv`).
옛 덤프를 읽으면 <b>거기서 죽는다</b> — 「상태가 없어 형태를 못 그린다」고 말하고.

### ② `tools/blockshape.py` — 블록 하나 → <b>상자 목록</b>

좌표는 마크 모델과 같은 <b>0..16</b> 단위다 (사람이 견주기 쉽다).

```
반블록   아래 (0,0,0)-(16,8,16) · 위 (0,8,0)-(16,16,16) · 겹은 풀블록
계단     밑판 + 윗단 = 부피 3/4 · inner 는 윗단 둘 · outer 는 4분의 1
트랩도어  열림 = 두께 3 <b>세운 판</b> · 닫힘 = 두께 3 눕힌 판
담장·울타리  가운데 기둥 + <b>이어진 쪽으로만</b> 팔
등롱     작은 상자 + 갓 · 배너 두께 2 판
```

★<b>모르는 블록은 정육면체로 그리되 이름을 센다</b> — 조용히 안 넘어간다.
「정육면체가 맞다」고 확인한 이름만 보고에서 빠진다.

눈 21개 — 반블록의 위치·계단의 부피와 방향·열린 트랩도어의 두께·담장 이음·모름 보고.

### ★자가 거짓말한 자리 하나 — 계단 방향

처음엔 「계단이 바라보는 쪽이 <b>낮다</b>」로 적었다. 그러자 지붕이
<b>빗살처럼 틈이 벌어져</b> 보였다 — 계단 층이 서로 안 맞물렸기 때문이다.
실물은 막혀 있는데 <b>도해가 거짓말을 했다.</b>

바닐라 모델을 보고 고쳤다: `block/stairs.json` 의 둘째 상자가 `[8,8,0]~[16,16,16]` = +x 이고
blockstate 가 `facing=east` 를 회전 0 으로 두므로 — <b>윗단은 facing 쪽</b>이다.

### ③ 뒤집을 때 <b>블록 안 좌표도</b> 뒤집는다

네 귀에서 보려고 x·z 를 뒤집는데, 블록 안 상자를 안 뒤집으면 <b>계단이 반대로 선다</b>.
같은 건물이 방향에 따라 다른 모양으로 보이면 그건 도해가 아니다.

### 결과

```
572×436 · 0.15초 · 덤프 11,001칸 · 색표가 블록을 전부 안다
```

지붕의 기와 결·처마의 계단 윤곽·난간의 담장 팔·등롱·배너가 <b>제 모양으로</b> 보인다.

## ⑥ 제안 — 공간 데이터로 학습한다 (2026-08-27 · 사용자 지시로 설계)

> 사용자 지시: 「최신 건축 방식에 맞춰 건축 AI 를 강화 — <b>공간 데이터로 학습하는 방법</b>」

### 왜 이것이 다음인가

지금 시스템이 배우는 원천은 <b>사진 한 장</b>뿐이다 (5지표·ref_measure). 그런데 그 사진은
렌더라 <b>블록이 없다</b> (§4-표준 ㉢ 실측 — 반복 조각 0건). 그래서 색·비례는 배워도
「그 비례를 <b>블록 1칸 최소 단위로</b> 어떻게 푸는가」는 매번 우리가 처음부터 풀었다 —
문선 회차가 그 값이다 (축척의 벽에 부딪혀 칸 주기를 갈아엎었다).

<b>블록으로 지어진 실물 공간 데이터에는 그 답이 있다.</b> 마크 커뮤니티의 한옥·동양 건축
명작 schematic 은 우리와 <b>같은 척도 제약</b>(블록 1칸 최소·같은 팔레트 후보) 아래서
같은 문제를 이미 푼 결과물이다. 그리고 우리 자신의 덤프(TSV·블록 상태 포함)가
이미 같은 정규형의 데이터다 — 학습 파이프라인은 외부 없이도 오늘 시작할 수 있다.

### ★「학습」의 뜻을 가른다 — 가중치가 아니라 문법·분포다

이 저장소에서 학습은 <b>코퍼스에서 문법과 분포를 캐는 것</b>이다. 신경망(복셀 생성 모델·
시퀀스 모델)이 아니다. 근거 셋:
1. 데이터 규모 — 코퍼스가 수십 채 규모라 생성 모델은 못 선다 (외우거나 뭉갠다)
2. <b>눈 문화와의 충돌</b> — 캐낸 규칙은 눈이 검사할 수 있어야 한다. 「모델이 그렇게
   출력했다」는 이 저장소에서 증거가 아니다
3. 그릇이 이미 있다 — 기법 그래프(`techniques.yml`)가 「배운 것을 담는 자리」다.
   학습의 출력이 <b>사전 증축 후보 diff</b> 가 되면, 사람이 검토하고 눈이 지킨다

(코퍼스가 수백 채를 넘고 문법 마이닝이 한계에 닿으면 그때 재론한다.)

### 단계 — 다섯 + 확장 하나

| # | 무엇 | 내용 · 왜 |
|---|---|---|
| E-1 | <b>정규형·수집</b> | `tools/schem_import.py`: `.schem`/`.litematic`/`.nbt` → 우리 덤프 TSV 정규형. 코퍼스는 `run/corpus/` (★저작권 — <b>저장소에 커밋하지 않는다</b>. 목록·출처·라이선스만 docs 에 적는다). ★어떤 명작을 넣을지는 <b>사용자 결정</b> — 코퍼스가 곧 취향의 정본이 된다. nbtlib 설치 필요 |
| E-2 | <b>수직 쌓임 캐기</b> | (x,z) 기둥별 y 열을 뽑아 런 압축 → 빈도순 쌓임 후보. ★<b>층 절단</b>이 관건 — 긴보(plate)·지반·지붕에서 잘라 몸통 문법만 남긴다 (아래 첫 실증의 교훈) |
| E-3 | <b>관계 통계</b> | 읽힘 자의 미해결 둘에 데이터로 답한다: ⓐ <b>격자 주기</b> — 세로 부재 간격 분포 (지금은 레퍼런스 한 장의 14선뿐) ⓑ <b>이웃 관계</b> — 인접 재료 쌍 통계 (「공포가 통짜로 뭉친다」를 이웃 다양성으로 잰다) ⓒ <b>지붕 프로파일</b> — (거리→높이) 곡선 분포 (물매·안허리곡 — 동쪽 4칸 미해결의 답 후보) |
| E-4 | <b>분포 눈</b> | 「오늘의 값을 외운 자」(실패 유형 ①)의 해독제 — 문턱을 처방이 아니라 <b>코퍼스 분포</b>에서 뽑는다 (세로 부재 밀도·어칸:협칸 비·팔레트 가짓수·부재 면적비). 눈은 「분포의 p10~p90 밖이면 짖는다」. 코퍼스가 갱신되면 문턱이 따라온다 — <b>표가 조용히 낡지 않는다</b> |
| E-5 | <b>사전 자동 증축</b> | E-2·3 출력을 `techniques.yml` <b>후보 diff</b> 로 낸다 (자동 반영 금지 — 검토 후 채택). 이로써 루프가 닫힌다: <b>학습 → 사전 → 설계기 → 도면 → 덤프 → 학습</b> |
| E-6 | (확장) 사진 자 보강 | 5지표에 격자 주기 자(자기상관)·명도 수직 프로파일 대조를 더한다 — 이미 있는 것의 소폭 확장 |

### 첫 실증 (2026-08-27 · 본전 덤프 11,001칸)

E-2 의 최소형을 스크래치로 돌렸다: 기둥 1,216개 → 고유 쌓임 99종.

- ★손으로 쓴 사전의 <b>「모든 쌓임의 끝 세 켜 = 창방·도리·긴보」</b>가 데이터에서 그대로
  나왔다 — 창호 기둥 상위 후보의 꼬리가 정확히 `mangrove_planks | dark_oak_slab |
  dark_oak_log` 다. <b>캐는 방법 자체는 선다.</b>
- ★교훈: 날것 그대로는 <b>지형·지붕 기둥이 상위를 덮는다</b> (1위 stone_bricks 176개 —
  포장이다). E-2 의 본체는 세는 것이 아니라 <b>층을 가르는 것</b>이다 —
  긴보가 몸통과 지붕을 가르는 정본 경계이므로, 사전의 layer 정보로 자른다.

### 하지 않는 것 (판단 근거와 함께)

- <b>복셀 생성 모델·시퀀스 모델</b> — 위 「학습의 뜻」 절. 재론 조건도 거기 적었다
- <b>레퍼런스 사진에서 깊이 추정으로 3D 복원</b> — 그 렌더는 기하가 일관되지 않다
  (반복 조각 0건 실측). 치수·비례·색 계열까지만 읽는다 (기존 결론 유지)
