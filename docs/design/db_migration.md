# DB 마이그레이션 절차 — 버전 스탬프 + 소급 스크립트

> 발단: 집안 기술 grants가 생성 시점에만 부여돼, 배선 이전 캐릭터는 승급 요건을
> 영구히 못 채우는 선례 (docs/bot/bot_alpha_guide.md "마이그레이션 선례" — 백로그).
> 시트 스키마(sheet_json 키 구조 포함)가 진화하면 기존 행 소급분이 반드시 생긴다.
> 실행기: `tools/migrate_db.py` / 등록부: `db/migrations/` / 첫 사례: 001 집안 grants 소급.

---

## 1. 원칙

1. **스키마·시트 변경에는 마이그레이션이 동반된다.** 다음 중 하나라도 해당하면
   `db/migrations/`에 마이그레이션을 함께 커밋한다:
   - `db/schema.sql` 변경 (테이블·컬럼·인덱스 추가) — `CREATE TABLE IF NOT EXISTS`로
     새 DB엔 적용되지만, **기존 DB의 기존 행 소급**은 스키마가 못 한다
   - JSON 컬럼(sheet_json·ledger_json·marks_json·state_json …) **키 구조 변경**,
     또는 "생성 시점에만 부여되는 값" 신설 — 001이 바로 이 유형
   - config 값 변경 자체는 마이그레이션 불요. 단 config가 DB에 이미 새겨진 값의
     원천이었다면(예: grants) 소급 여부를 검토한다
2. **버전 스탬프**: `world_meta` 키 `'스키마_버전'`. 행이 없으면 0으로 간주
   (알파 기존 DB = 버전 0). 각 마이그레이션 커밋 시 이 값이 파일 번호로 올라간다.
3. **내부 키 불변 원칙(terminology_policy.md)이 1차 방어선이다** — 표시층 치환으로
   DB 키 개명 마이그레이션 자체를 피한다. 마이그레이션은 피할 수 없는 구조 변화용.
4. **마이그레이션은 시점 고정 스크립트다.** 작성 당시의 규칙을 그대로 새긴다 —
   이후 config가 바뀌어도 과거 마이그레이션은 수정하지 않는다(이미 적용된 DB와
   어긋난다). 적용 완료된 마이그레이션 파일은 영구 불변.

## 2. 번호·파일 규약

- 경로: `db/migrations/NNN_설명.sql` 또는 `NNN_설명.py`
  - `NNN` = 3자리 0채움 일련번호. **중복 금지**(실행기가 거부), 결번은 허용하되 피한다.
  - `.sql` — DDL·단순 UPDATE. 문장 단위로 실행된다 (트랜잭션은 실행기가 건다 —
    파일 안에 BEGIN/COMMIT 쓰지 말 것).
  - `.py` — JSON 컬럼 소급처럼 SQL만으로 어려운 것. `def migrate(conn)`을 정의한다
    (`conn` = `sqlite3.Connection`, 이미 트랜잭션 안. 커밋/롤백은 실행기 몫).
    문자열을 반환하면 적용 로그에 요약으로 찍힌다.
- 번호 순서 = 적용 순서. 현재 `스키마_버전`보다 큰 번호만 순차 적용된다.

## 3. 백업 규약

- 실행기가 **각 마이그레이션 적용 직전** `<db파일명>.pre-migrate-N-backup`을
  자동 생성한다 (예: `honcheon.db.pre-migrate-1-backup`). sqlite backup API 사용 —
  WAL 미체크포인트 내용까지 포함되므로 단순 파일 복사보다 안전하다.
- 복구: 봇 정지 상태에서 백업 파일을 원래 이름으로 되돌린다
  (`-wal`/`-shm` 잔여 파일은 삭제).
- 백업 파일은 커밋하지 않는다. 정식 운영 후 며칠 관찰하고 지운다.

## 4. 로컬 적용 순서 (운영 DB)

단일 작성자 원칙(persistence.md) 때문에 **봇이 켜진 채 실행 금지**.

```
1. 봇 정지
2. python3 tools/migrate_db.py data/honcheon.db --status   # 현재 버전·대기 확인
3. python3 tools/migrate_db.py data/honcheon.db --dry-run  # 적용 대상 재확인
4. python3 tools/migrate_db.py data/honcheon.db            # 백업 자동 생성 후 순차 적용
5. 출력에서 "완료: 스키마_버전 X → Y" 확인 (실패 시 자동 롤백·중단 — 백업으로 복구 가능)
6. 봇 재기동 → 소급 대상 캐릭터로 동작 확인 (예: 001이면 캐릭터 시트에 기술 표시)
```

각 단계는 독립 트랜잭션(버전 스탬프 포함)이다 — N번이 실패하면 N-1까지는 적용된
채로 남고, 재실행하면 N부터 다시 시도한다.

## 5. 테스트 방법 (마이그레이션 작성 시 의무)

새 마이그레이션은 커밋 전에 임시 DB로 왕복 검증한다:

```
1. 임시 DB 생성: sqlite3로 db/schema.sql 실행 + world_meta '현재일' 삽입
2. "구식" 행 삽입 — 마이그레이션이 고치려는 과거 형태 그대로
   (001 예: sheet_json에 "기술" 키 없음, "집안"은 공백 표기 "몰락 무가의 자식")
3. 경계 케이스 행 삽입 — 이미 신식인 행(불변이어야 함), 대상 아닌 행
4. --status → --dry-run(무변경 확인) → 실적용 → 결과·버전 스탬프·백업 확인
5. 재실행 → "이미 최신" no-op(멱등성) 확인
6. 실패 경로: 일부러 깨지는 문장을 넣어 롤백·중단(exit 1, 버전 불변)도 한 번 확인
```

001은 이 절차로 검증 완료: 구식 3명 소급(몰락 무가→검법 0, 무가→검법 1,
객잔집→고객_파악 1), 기술 보유 2명 불변(이중 부여 방지), 농가(기술 grants 없음)
불변, 멱등성·롤백 확인.

## 6. 적용된 마이그레이션 대장

| 번호 | 파일 | 내용 | 비고 |
|---|---|---|---|
| 001 | `001_family_grants_소급.py` | 배선 이전 캐릭터에 집안 기술 grants 소급 (sheet_json "기술" 키 부재 시 config families grants.기술 주입) | bot_alpha_guide 선례 해소 |

## 7. 남은 배선 (후속)

- **Java 쪽 버전 게이트**: `Db.java` 생성자에서 `world_meta '스키마_버전'`을 읽어
  등록부 최신 번호보다 낮으면 기동 거부(또는 경고 로그)하는 배선 — 마이그레이션
  누락 상태로 봇이 구 스키마 위에서 돌아가는 사고 방지. 자동 실행까지는 하지 않는다
  (마이그레이션은 사람이 백업 확인 후 돌리는 절차로 유지).
- 새 DB(schema.sql로 갓 생성)의 초기 버전 스탬프: 현재는 첫 migrate 실행이 찍는다.
  Java 배선 시 생성 직후 최신 번호로 스탬프하면 신규 DB의 불필요한 소급 실행을 건너뛸
  수 있다 (001은 멱등이라 지금도 실해는 없음).
