# 스킬 모션 디자인 루프 도구 (2026-07-20)

## 무엇을 만드는가

**인게임에서 스킬 모션을 디자인할 때 「바꾸고 → 보고 → 또 바꾸는」 고리를 빠르게 돌리는 도구.**
무기 스킬·몹 스킬·보스 스킬 전부에 쓴다. 회귀 검증 도구가 아니다 — **디자인 도구**다.

두 번 헛짚었으니 적어 둔다:
- v0 은 검기 전용 회귀 검증이었다 ("안 깨졌나")
- v1 계획은 신뢰성만 팠다 (필요했지만 그것만으로는 디자인이 안 된다)
- **v2 의 물음은 하나다: 얼마나 빨리 다시 볼 수 있는가**

## 지금 루프가 왜 느린가 (실측)

값 하나를 바꾸려면:

```
config 수정 → 서버 재기동(20초) → 클라 재접속(소프트렌더라 60~180초)
→ 무대 재설치 → 촬영 → 판독          ≈ 3~5분
```

병목은 **`skill_motion.yml` 이 `onEnable` 에서만 읽히는 것**이다
(`HoncheonMvt.java:69  this.skillEngine = new SkillEngine(cfg)`).
값 하나 때문에 서버를 내리면 클라 접속까지 끊기고, 그 재접속이 가장 비싸다.

검기 작업에서 이 고리를 **수십 번** 돌았다. 그때마다 3~5분이었다.

---

## 핵심 = 루프 속도 (목표 10~20초)

### ① config 핫 리로드 — 가장 큰 승부처
`/혼천 모션 재적재` — 서버를 내리지 않고 `skill_motion.yml` 을 **다시 읽는다**.
`SkillEngine` 을 새로 만들어 참조를 갈아끼운다 (검기 오버라이드에서 이미 비슷한 짓을 했다).

```
config 수정 → /혼천 모션 재적재 → 스킬 발동 → 본다        ≈ 10초
```

**클라를 안 끊는다**는 게 핵심이다. 재접속이 사라지면 루프가 20배 빨라진다.

### ② 아무 스킬이나 발동
- `--trigger "<rcon 명령>"` — 무기 스킬·몹 스킬·보스 스킬 무엇이든
- **한글 명령도 RCON 으로는 된다** (xdotool 은 한글을 뭉갠다 — 그래서 막혔었다)
- `--summon <몹>` 몹을 세우고 그 스킬을 본다
- `--wait-natural` 몹이 제 AI 로 쓸 때까지 기다려 잡는다

### ③ 즉시 보이는 산출
디자인 도구는 숫자로 닫지 않는다. **바로 볼 것**을 낸다:
- **연속 프레임 시트** (지금도 있다)
- **움직이는 미리보기** (GIF/APNG) — 모션은 정지 화면으로 판단할 수 없다
- **직전 실행과 나란히** — "방금 바꾼 게 나아졌나"가 루프의 실제 물음이다

### ④ 색을 모른 채 재기
지금은 초록 문턱이 박혀 있어 **검기 말고는 못 본다.** 스킬마다 색이 다르다.
- 발동 전 유휴 프레임 → 배경·HUD 정적 마스크
- 발동 후 차분만 남겨 **색 분포를 스스로 산출**
- 색 견본을 산출에 함께 — "이 스킬은 무슨 색인가"를 눈으로

---

## 그다음 (루프가 돌기 시작한 뒤)

루프가 빨라지면 그때 쓸모가 생기는 것들. 지금 만들면 이르다.

- **시간축**: 응집(선딜) → 발출 → 여운. 프레임별 면적 곡선으로 단계 경계
- **공간축**: 중심 좌표 궤적 — 머무나·날아가나·퍼지나
- **구별성**: 두 스킬이 비슷해 보이면 플레이어가 반응 못 한다. 색·모양·타임라인 대조
- **예고 가독성**: 선딜이 **1인칭에서** 몇 px·몇 틱 보이나 (싸우는 시점에서 보여야 한다)
- **카탈로그**: 스킬 전체의 시각 색인 — 새 스킬이 기존과 겹치나
- **부하**: 몹 N마리 동시 시전 시 파티클·엔티티·TPS

## 물려받는 원칙 (v1 에서 — 이건 버리지 않는다)

1. **조용히 틀리지 않는다** — 전제가 깨지면 0 을 뱉지 말고 측정을 거부 (`vfx_preflight`)
2. **눈을 시험하는 눈** — 검출기를 매 실행 자가시험 (`vfx_detect`)
3. **보여 준다** — 디자인 도구는 그림이 함께 나와야 한다

핫 리로드가 생기면 preflight 의 「config 동기화」 검사가 더 중요해진다 —
**리로드했다고 믿었는데 안 된 경우**를 잡아야 하기 때문이다.

## 순서

1. **핫 리로드** (`/혼천 모션 재적재`) — 이것 없이는 나머지가 다 느리다
2. **임의 발동 + 색 자동 보정** — 검기 밖으로 나간다
3. **움직이는 미리보기 + 직전 대조** — 루프의 눈
4. 그다음은 실제로 스킬을 디자인해 보며 아쉬운 것부터

# 자동 루프 — AI 가 스스로 닫는다 (2026-07-20 · 사용자 확정)

## 이 도구의 진짜 목적

**사람이 접속해 확인하지 않아도, AI 가 제가 만든 스킬의 인게임 디자인을 보고
루프를 돌려 스스로 고친다.** 대상은 무기별 공격 이펙트 · 몹/보스 공격 이펙트 · 스킬 모션.

앞의 계획(속도·일반화·신뢰성)은 이 루프의 **눈과 손**이다. 그것만으로는 루프가 닫히지 않는다 —
**"이게 맞나"를 답하는 판단 층**이 있어야 한다. 그것이 빠져 있었다.

## 자동 판단의 경계 (확정)

| AI 가 판단한다 | 사람에게 묻는다 |
|---|---|
| 보이는가 · 어느 각도에서 · 몇 px | 예쁜가 · 멋있는가 |
| 얼마나 오래 · 어디로 움직이나 | 세계관 톤에 맞는가 |
| 무슨 색인가 | 맞서 싸울 때 기분이 좋은가 |
| **레퍼런스와 얼마나 닮았나** (구조 유사도) | |
| **다른 스킬과 구별되나** (색·모양·타임라인 대조) | |
| 히트박스와 일치하나 (「보이는 모양이 맞는 모양이다」) | |

왼쪽은 자동으로 돈다. 오른쪽은 **AI 가 요청하고 사람이 확인·검토한다.**

## 루프

```
[명세]  사람이 목표를 준다 — 레퍼런스 그림 / 필수 조건 / 금지 조건
   ↓
[생성]  AI 가 값·에셋을 만든다
   ↓
[적용]  핫 리로드 (10초 · 클라를 안 끊는다)
   ↓
[관측]  네 각도 촬영 + 측정      ← preflight 가 「조건이 성한가」를 보증
   ↓
[판정]  객관 기준으로 자동 채점  ← vfx_detect 가 「눈이 성한가」를 보증
   ├─ 충족  → [사람 호출] "객관 기준 통과. 미감 확인 부탁드립니다" + 그림
   ├─ 미달  → [수정] 부족한 축을 골라 값 조정 → 적용으로 되돌아간다
   └─ 막힘  → [사람 호출] "N회 개선 없음. 이 방향이 맞는지 판단 필요" + 시도 기록
```

## 명세 — 기계가 읽는 목표

루프를 시작하려면 **무엇을 만들려는가**가 기계가 읽을 수 있게 적혀야 한다.

```yaml
스킬: 화산_매화검_3식
레퍼런스: 작업물/레퍼런스/매화검_3식.png      # 있으면 구조 유사도로 채점
필수:
  가시성: { 3인칭뒤: ">=2000px", 1인칭: ">=800px" }
  지속:   { 최소: 0.4초, 최대: 1.2초 }
  색:     { 계열: 분홍, 채도: "<=130" }        # 형광 금지는 이 저장소의 기존 원칙
금지:
  유사: [화산_매화검_2식]                       # 첫 6틱이 닮으면 실패
```

## 멈추는 조건 (수렴)

- **충족**: 필수 전부 통과 → 사람 호출
- **정체**: N회(기본 5) 연속 개선 없음 → 사람 호출 (헛도는 것을 스스로 인정한다)
- **상한**: 최대 반복(기본 15) → 사람 호출
- **조건 파손**: preflight 실패 → **즉시 중단** (틀린 눈으로 고치면 디자인이 망가진다)

## 왜 사람 호출 지점이 반드시 있어야 하나 (오늘의 증거)

2026-07-20 하루 동안 AI(조율자)는 눈도 손도 있었지만 **일곱 번 조용히 틀렸다**:
검출 문턱 불일치 · 팩 무시 · HUD 오염 · 파서 불일치 · 메모리 누수 · 팩 캐시 · 로그 혼동.
그중 두 번은 **사용자가 짚어 주어서** 잡혔다 ("전혀 다른데?", "프레임도 적용 안 된 것 같은데요").
사람이 안 짚었다면 멀쩡한 회전 코드를 헤집었을 것이다.

⇒ 자동 루프는 오판을 **증폭**한다. 그래서:
1. preflight·self-test 가 **조건과 눈**을 매번 검사하고, 어긋나면 **측정을 거부**한다 (0 을 「효과 없음」으로 읽지 않는다)
2. 사람 호출 때는 **주장이 아니라 증거**를 낸다 — 그림·수치·시도 기록
3. 막히면 스스로 인정하고 부른다. 억지로 수렴하지 않는다


## 사람 확인은 2단계다 (사용자 확정)

AI 가 사람을 부를 때 **곧바로 인게임 접속을 요구하지 않는다.** 값싼 것부터 쓴다.

```
[1차]  하네스가 만든 그림으로 확인       ← 대개 여기서 끝난다
   ├─ 판단 가능 → 확정 / 수정 지시
   └─ 부족하다 → [2차] 플레이어가 접속해 직접 확인
```

**왜 이 순서인가**: 접속해서 무기 꺼내고 휘두르고 녹화하는 일은 사람의 시간을 크게 쓴다.
그림으로 답할 수 있는 물음까지 접속을 요구하면 루프의 의미가 없다.

### 그러므로 1차 그림이 **판단에 충분해야** 한다
- **네 각도**를 함께 (뒤·앞·옆·위) — 한 각도만 보면 오늘처럼 오판한다
- **움직이는 미리보기**(GIF) — 모션은 정지 화면으로 판단할 수 없다
- **직전 값과 나란히** — "방금 바꾼 게 나아졌나"
- **preflight 결과를 함께** — "이 그림은 조건이 성한 상태에서 찍혔다"는 보증이 없으면
  그림 자체가 거짓말일 수 있다 (오늘 옛 팩을 보며 판단할 뻔했다)
- **한계를 적는다** — 소프트렌더 6~7fps · 실제 게임은 더 부드럽다 · 색은 조명에 따라 다르다

### 2차(접속)로 넘길 때
AI 는 **무엇을 봐 달라는지 구체적으로** 적는다 — "이상한지 봐 주세요" 가 아니라
"1인칭에서 검기가 화면을 덮는지" 처럼 **그림으로 답이 안 나온 물음 하나**를 짚는다.

# 테스트 서버의 앞날 — 스테이징 환경으로 (2026-07-20 · 사용자 방향)

지금 `run/mvt-test` 는 시각효과를 보려고 세운 모래상자다(평지·최소 구성).
앞으로는 **본서버 전 검증 환경**이 된다: 스탯 시험 → 스킬별 밸런스 → 본서버 이행.

## 그러면 요구가 달라진다

| | 지금 (VFX 모래상자) | 앞으로 (스테이징) |
|---|---|---|
| 월드 | 평지 flat · 최소 | 라이브에 가까운 사본 |
| 데이터 | 없음 (봇만 접속) | **캐릭터·스탯·경지** 가 필요 |
| 물음 | "이렇게 보이나" | "이 수치가 맞나 · 밸런스가 서나" |
| 도구 | 화면 촬영·픽셀 판독 | **전투 수치**(피해·TTK·명중·소모) |
| 산출 | 그림 | 표·곡선 |

## ★ 먼저 못박을 위험 — 데이터 격리

**스탯·밸런스를 시험하려면 캐릭터 데이터가 필요하고, 그 순간 라이브 DB 를 건드릴 위험이 생긴다.**

- 운영 DB 는 **PostgreSQL** (`honcheon-postgres` · `127.0.0.1:5435`) — [[prod-postgres-cutover]]
- 2026-07-20 실측: 테스트 서버는 **열린 .db 가 없다** (아직 캐릭터를 안 쓴다). 지금은 격리돼 있다.
- 스테이징으로 넘어갈 때 **반드시** 먼저 정할 것:
  1. 테스트 전용 DB (별도 스키마 또는 별도 컨테이너 · 포트)
  2. 라이브에서 **읽기만** 하는 스냅샷을 뜨는 절차 (쓰기 경로를 아예 끊는다)
  3. 테스트가 라이브 DB 에 **쓸 수 없음을 기계가 보증** — preflight 에 「DB 대상이 테스트인가」 항목 추가

**되돌릴 수 없는 것부터 못박는다**: 시각효과는 틀려도 다시 찍으면 되지만,
운영 데이터는 한 번 오염되면 되돌릴 수 없다.

## 이행 경로 (test → live)

지금은 사람이 `scripts/redeploy_mvt.sh` 로 손수 옮긴다. 스테이징이 되면 절차가 필요하다:
- 테스트에서 **무엇이 검증됐는지** 기록 (루프 산출물 · 밸런스 표)
- 라이브/테스트 프로세스 구분은 **cwd 로** 한다 — 명령줄 플래그로 가르지 마라
  (2026-07-20 에 두 번 사고: `paper.jar` 로 찾아 테스트까지 잡았고, `-Xms2G` 로 좁혔더니 테스트도 같은 플래그가 됐다)

## 지금 만드는 것 중 그대로 쓰이는 것

- `vfx_preflight` — 「조건이 성한가」는 밸런스 시험에도 그대로 필요하다 (옛 jar·옛 config 로 잰 수치는 거짓말이다)
- 핫 리로드 — 수치 조정 루프에서 더 크게 쓰인다 (밸런스는 값을 훨씬 자주 만진다)
- 자동 루프의 뼈대(명세 → 관측 → 채점 → 조정) — 채점 기준만 「그림」에서 「수치」로 바뀐다

## 데이터 격리 — 같은 DB, 방향이 다른 권한 (사용자 확정 2026-07-20)

**요구**: 테스트는 본서버 데이터를 **가져와** 시험할 수 있다. 본서버는 테스트 데이터를 **못 받는다.**
즉 흐름이 한 방향이다: `라이브 → 테스트` 는 열고, `테스트 → 라이브` 는 막는다.

같은 PostgreSQL 인스턴스를 쓰되 **역할(role)로 방향을 강제**한다.

```
스키마      honcheon        (라이브 정본)
            honcheon_test   (테스트 전용)

역할        honcheon_live   : honcheon 읽기/쓰기 · honcheon_test 없음
```

테스트 서버는 그 역할로만 붙는다. **코드가 실수해도 DB 가 거절한다** — 앱이 아니라 DB 가 막는 것이 핵심이다.

### 왜 스키마 분리만으로는 부족한가
`search_path` 는 세션 설정이라 **틀릴 수 있고, 틀려도 조용하다** (오늘 일곱 번 겪은 그 부류다).
권한은 다르다 — 틀리면 **에러가 난다.** 조용히 오염되느니 시끄럽게 실패하는 편이 낫다.

### ★ 먼저 막아야 할 더 큰 구멍 — 브리지
MVT 플러그인에는 **DB 연결 코드가 없다**(실측). DB 를 쓰는 것은 봇뿐이고,
MVT 는 **파일 브리지**로 봇에게 사건을 넘긴다:

```
world_bridge.yml  transport.dir: run/bridge     ← 라이브·테스트가 **같은 경로**
                  outbox: mvt                    → run/bridge/mvt/<날짜>.jsonl
```

**즉 테스트 서버가 쓴 사건이 라이브 봇에게 그대로 흘러가 운영 DB 에 기록된다.**
DB 권한을 아무리 나눠도 이 경로가 열려 있으면 소용없다 — 쓰는 주체가 라이브 봇이기 때문이다.

- 2026-07-20 실측: 오염 **없음** (`kigibot`·`kigicam` 사건 0건). 테스트가 아직 브리지에 쓸 행동을 안 했을 뿐,
  **구조는 열려 있다.** 스탯·밸런스 시험을 시작하면 즉시 샌다.
- 조치: 테스트의 `transport.dir` 을 `run/bridge-test` 로 가른다. 그리고 preflight 에
  「테스트의 브리지 경로가 라이브와 다른가」를 넣어 **다르지 않으면 측정을 거부**한다.

### 검증은 가정하지 않는다
격리를 만들었으면 **작동하는지 시험한다** (이 저장소 관례: 눈을 시험하는 눈):
- 테스트 역할로 라이브 스키마에 **일부러 INSERT 를 시도** → 거절당해야 통과
- 테스트가 브리지에 쓴 사건이 라이브 봇 커서에 **안 잡히는지** 확인
- 두 시험을 preflight 에 넣어 매 실행 검사
