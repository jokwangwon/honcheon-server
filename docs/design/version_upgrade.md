### 0.1 3차 개정 — **판단이 바뀌었다** (가구·표현력 축)

사용자 주장: *"마크 신버전에는 **방석도 있고 의자도 생겼다**고 들었는데, 이런 **기능적 측면**도 고려해서
업그레이드가 좋을 것 같다. **몹 오브젝트 개선**도 있으니 **표현력의 확장성**도 늘었다."*

**검증 결과: 사용자가 옳다. 그리고 1·2차 조사가 이 축을 통째로 안 봤다.** 다만 **버전을 한 칸 잘못 짚었다** —
그 가구는 26.1도 26.2도 아닌 **26.3(미출시)**에 있다. 정확히 판정하면:

| 사용자 주장 | 판정 | 실제 |
|---|---|---|
| "**방석**이 생겼다" | ✅ **사실** | **`cushion`** — 16색, **실제로 앉는다**(use 키). 단 **26.3 스냅샷 3**(2026-07-07), **미출시** |
| "**의자**도 생겼다" | ⚠️ **절반 사실** | **의자 블록은 없다.** 방석은 충돌 판정이 없어 **계단 위에 얹을 수 있고**, 그것이 의자다. → **우리의 "계단 걸상"이 그대로 진짜 의자가 된다** |
| "**몹 오브젝트 개선**"으로 표현력 확장 | ❌ **우리에겐 아니다** | 26.1의 몹 개선은 **아기몹 리모델**이다. 우리는 아기몹을 안 쓴다. **표현력 확장은 26.x가 아니라 1.21.9의 `mannequin`이 준다**(§8.3) |
| "그러니 **업그레이드가 좋다**" | ✅ **결론은 옳다** | 다만 **목적지가 26.3**이고, **지금은 갈 수 없다**(미출시). **1.21.11 → 26.3** 2단 이주가 답이다 |

**무엇이 뒤집혔나 — 정직하게:**

```text
2차 결론: "26.x는 갈 이유가 없다"           → 26.1·26.2에 대해서는 여전히 참이다
3차 발견: "26.3은 갈 이유가 명확히 있다"     → 가구다. 그리고 §6.7이 스스로 건 재평가 조건
                                              ①"26.3 출시 후 블록 추가분을 다시 센다"가 **발동했다**
```

2차 조사는 **"26.x = 성능 이득 0"**이라 했고 그건 **지금도 맞다**. 틀린 것은 **"그러므로 26.x는 무가치하다"**는
확장이었다. **26.3의 가치는 성능이 아니라 가구다.** 그리고 우리 실내가 빈약한 근본 원인이 바로 가구의 부재다.

**세 줄 요약:**
1. **지금**: 1.21.11로 간다 — **판단 유지**. 시렁·창살·등롱·창을 수확하고, **선반 도난 문제도 해결됐다**(§8.2).
2. **26.3 출시 시(Q3 2026, 임박)**: **간다.** 방석·짚 침상·양털 계단/반블록이 **우리 흉내의 절반을 실물로 바꾼다**(§8.1).
3. **26.1·26.2**: **끝까지 안 간다.** 가구 0 · 성능 0 · 툴체인 비용만 있다. **26.3을 위해 건너뛴다.**

### 0.1 2차 개정 — 무엇이 바뀌었나 (성능·기술 축)

사용자 반문: *"26버전으로 갔을 때 성능·기술 면에서 업그레이드가 된다면 좋을 것 같은데,
그걸 포함해서도 별로라고 생각하니?"* — **정당한 반문이었다. 1차 조사는 블록 축만 봤다.**

성능·기술 축을 실측한 결과 **결론은 유지되지만, 1차 조사의 근거 3개가 틀렸다.** 정직하게 적는다:

| 1차 조사의 주장 | 2차 실측 | 판정 |
|---|---|---|
| "26.x는 코드 비용이 더 크다" (문헌 추정) | **26.1.2 실컴파일 = 6에러. 1.21.11과 완전히 동일한 심볼.** 고치면 둘 다 0에러 | ❌ **틀렸다** |
| "26.1은 월드 마이그레이션 버그가 있다" | Paper #13740·#13749 **둘 다 CLOSED**(2026-04) | ❌ **철 지났다** |
| "26.1은 Java 25를 요구한다 = 26.x의 비용" | 맞다. 그러나 **Java 25는 1.21.11에서도 쓸 수 있다**(부팅 실측). Java 25는 26.x의 *이득*이 아니라 *입장료*다 | ⚠️ **프레이밍 오류** |

**그런데 결론은 그대로다 — 더 강해졌다.** 이유가 바뀌었기 때문이다:

```text
1차 논리: "26.x는 비용이 크다"          → 틀렸다. 코드 비용은 같다.
2차 논리: "26.x는 성능·기술 이득이 0이다" → 실측으로 확인. 이게 진짜 이유다.
```

- **26.1: 청크 생성·저장 포맷 변화 없음. 서버 성능 개선 없음.** (minecraft.wiki 전수 확인)
- **26.2: Vulkan은 클라이언트 전용이다.** 서버는 한 톨도 안 빨라진다.
- **Paper의 청크 시스템 재작성(Moonrise)은 이미 우리 1.21.4에 들어 있다.** 26.x가 새로 주는 게 아니다.
- **Java 25 = 26.x의 독점 이득이 아니다.** Paper 1.21.11이 Java 25에서 **정상 부팅한다(실측)**.
  → 26.x로 안 가고도 Java 25를 취할 수 있다. **26.x의 마지막 기술적 명분이 사라진다.**
- **결정적: Java 25로 우리 청크 생성이 안 빨라진다 — 실측했다.** (§6.3, 21 vs 25 = 노이즈 범위)

**그리고 진짜 병목을 찾았다(§6.5).** 우리의 성능 문제는 버전이 아니다:
`CheonghaBuilder`가 **한 틱 안에 동기 블록 API를 ~75만~95만 회** 호출한다. 배치도 스케줄러도 없다.
**어떤 마인크래프트 버전도, 어떤 JDK도 이것을 고쳐 주지 않는다.** 성능을 원하면 **여기를 고쳐야 한다.**

### 1.2 버전 번호 체계가 바뀌었다

Mojang은 **2026년부터 `연도.드롭.핫픽스` 달력 버저닝**으로 갈아탔다. `1.21.11` 다음이 `26.1`이다.
"1.22"는 **존재하지 않는다.** 26.1은 또한 **최초의 완전 비난독화 릴리스**다.

### 1.3 "최신 = 블록 많다"는 이 경우 틀렸다

블록 증가량의 실체:

```text
1.21.5   자연물 6~7종      ← 쓸 것 있다
1.21.9   구리 6계열 × 4단 + 선반 13종   ← 대박
1.21.11  창(무기) 7단      ← 대박 (블록은 아니지만 우리 blocker를 푼다)
26.1     골든 민들레 1개    ← 없다시피
26.2     황·진사 2계열      ← 진사(cinnabar = 朱砂)는 매력적이나 알파다
```

**블록의 90%가 1.21.9에 있다.** 26.x로 더 가도 얻는 블록은 황(黃)과 진사뿐이고, 황은 무협에 쓸 데가 없다.

### 2.2 정직한 요약

`building_style_guide.md`가 아쉬워한 **6개** — 창살·시렁·등롱·족자·병풍·기와:

```text
창살  ✅ copper_bars (1.21.9)          — 오염 0 징발 슬롯
시렁  ✅ *_shelf (1.21.9)              — 흉내가 아니라 실물. 최대 이득
등롱  ✅ copper_lantern + copper_chain — 바닐라 lantern 징발을 취소할 수 있다
족자  ✅ painting 징발 (이미 해결됨)
병풍  ❌ 여전히 없다
기와  ❌ 여전히 없다 — deepslate_tiles 징발은 계속된다
```

**중요**: 새 블록은 **징발을 없애 주지 않는다.** 기와·회벽이라는 우리 정체성의 두 축은 **여전히 전역 치환**이다.
새 블록이 주는 것은 **징발 등록부의 여유**다 — 구리 계열은 전부 **제작 전용·자연 생성 0**이라
"세계의 어딘가를 내준다"는 대가 없이 징발할 수 있는 **12개 채널**(4산화단계 × 창살·등롱·사슬)이 새로 생긴다.
`texture_layer_design.md` §3.3이 "징발 등록부가 고갈되면 그때 blockstate 트릭을 다시 연다"고 했는데,
**등록부가 고갈되기는커녕 늘었다.** 트릭 불채택 결정은 더 튼튼해진다.

### 2.3 구리의 함정 — 수묵 정체성과 정면 충돌한다

`TownAudit.java:99` — `isColored()`는 **이름에 `COPPER`가 들어가면 무조건 유색으로 친다.**
`building_style_guide.md` §3.3 검수 기준도 "채색 블록(양털·**구리**·벚나무)이 차양 5·매화·민가 지붕 2채 밖에 없다"이다.

즉 **구리 창살·구리 등롱을 마을에 박으면 수묵 검수가 즉시 깨진다.**
구리는 주황(신품)이고 산화하면 청록(綠靑)이다. 둘 다 우리 팔레트에 없다.

해법은 둘 중 하나 — **메인이 골라야 한다**:

- **(A) 팩으로 덮는다.** `copper_bars`/`copper_lantern`을 먹빛으로 재텍스처. 제작 전용이라 오염 0.
  대가: **팩 게이트 위반 위험** — 팩 없는 클라에서 마을에 주황 창살이 박힌다.
  완화: **산화 단계를 고른다.** `weathered_*`(탁한 갈청)나 `oxidized_*`(청록)를 쓰면 팩 없이도
  "낡은 금속 창살"로 읽힌다 — 주황(신품)보다 훨씬 덜 튄다. `TownAudit.isColored()`에
  **"산화 구리는 유색이 아니다"** 예외를 넣는 것이 정합적 개정이다.
- **(B) 안 쓴다.** 선반(`*_shelf` — 목재라 무채색 안전)과 창(`*_spear`)만 취하고 구리는 보류.
  **이득의 절반을 버리지만 정체성은 한 줄도 안 건드린다.**

**조사자 권고: (A) + `weathered_` 산화 단계.** 이유는 `soul_lantern`(냉색)을 이미 "의미 있는 색"으로
쓰고 있듯, 낡은 구리의 갈청은 **"세월"의 색**이고 그것은 향촌 건축의 정서다. 다만 이건 **디자인 판단**이라
메인/사용자가 결정할 몫이다.

## 4. 판단

### 4.1 왜 1.21.11인가 (26.x가 아니라)

```text
이득 (블록·아이템):   1.21.11 이 26.2 의 ~95%  — 26.x가 더 주는 건 골든민들레·황·진사뿐
이득 (성능·기술):     26.x가 더 주는 것 ≈ 0    — §6에서 실측. 이것이 결정적이다
비용:                 1.21.11 = 6줄 + Java 21 유지 + Gradle 8.12 유지
                      26.1    = 6줄(동일!) + JDK 25 필수 + Gradle 8→9 메이저 업그레이드
                      26.2    = 위 전부 + Paper ALPHA (릴리스 후 한 달 넘게 안정판 없음)
```

> **정정(2차 조사):** 위에서 ~~"26.1 = 6줄 + 마이그레이션 버그"~~라고 썼던 부분을 고쳤다.
> **26.1의 코드 비용은 1.21.11과 똑같은 6줄이다**(실측). **마이그레이션 버그는 닫혔다.**
> 26.x를 반대하는 진짜 근거는 **비용이 아니라 이득의 부재**다 — §6.
> 다만 **빌드 툴체인 비용(Gradle 8→9)**은 1차 조사가 놓쳤던 **실재하는 신규 비용**이다.

**1.21.11은 파레토 최적이다.** 이득을 거의 다 가져오면서 비용은 6줄이다.
게다가 **Java 21을 요구하는 마지막 버전**이라, 여기서 멈추면 JDK 이주를 M3 이후로 미룰 수 있다.

### 4.2 왜 지금인가

**`texture_layer_design.md` §4.2 "2차 — 건축 자산(블록 징발)"에 착수하기 전에 해야 한다.**

지금 1.21.4 기준으로 블록 징발 등록부를 확정하고 텍스처 16~20장을 그린 뒤에 버전을 올리면,
구리 계열이라는 **오염 0 징발 슬롯 12개**가 뒤늦게 등장해서 **등록부를 다시 짜고 텍스처를 다시 그린다.**
지금 이주하면 등록부를 **한 번만** 짠다.

역으로 **1차(아이템 채널 38장)는 버전과 무관하다** — `item_model` 문법이 1.21.4~1.21.11 동일하므로
1차를 하면서 병행 이주해도 손실이 없다.

### 4.3 가장 큰 이득 3

1. **시렁(`*_shelf`) — 흉내의 종말.** 지금 우리의 "선반"은 물건을 올릴 수 없는 반블록이다.
   진짜 선반은 3칸에 아이템을 **진열**한다. 진철산의 오호단문창이 병장기 시렁에 **실제로 놓이고**,
   유문의 약장에 약재가 **보인다**. `npc_visual_design`의 "정위치 소품" 원칙이 비로소 물리적으로 성립한다.
2. **창(`*_spear`) — blocker 해소.** `spear_base_pending`이 반년째 "trident 투척 차단 접합 선행"에
   묶여 있었다. 바닐라 창은 **투척 불가**다 — 접합 조건 자체가 사라진다. 무공 계열 5종 중 하나가 풀린다.
3. **오염 0 징발 슬롯 12개.** 구리 4산화단계 × (창살·등롱·사슬). 제작 전용·자연 생성 0.
   "블록 채널은 교환이므로 늘릴 때마다 세계를 내준다"는 §1의 제약이 **처음으로 완화된다.**

### 4.4 가장 큰 위험 3

1. **리소스팩 재검증 — 최대 미지수.** `build_resourcepack.py`의 엔티티 UV 언랩(§2074~)이
   **1.21.4 바닐라 바이트코드에 명시적으로 결합**돼 있다. HUD 스프라이트 아틀라스도 마찬가지.
   *이것이 이주 비용의 90%다. 코드 6줄이 싸 보이는 것에 속으면 안 된다.*
2. **구리 = 유색.** 수묵 정체성과 정면 충돌한다(§2.3). `TownAudit.isColored()`가 즉시 잡아낸다.
   팩 없는 클라에서 마을에 주황이 박힐 위험 — **팩 게이트 제1원칙 위반 가능성.**
   산화 단계 선택(`weathered_`)으로 완화 가능하나 **디자인 결정이 선행돼야 한다.**
3. **선반은 상호작용 블록이다.** 우클릭하면 핫바와 내용물이 **교환**된다 — 플레이어가 진열품(비급·창·약재)을
   **훔칠 수 있다.** `bundle`/`name_tag`/`lead`와 같은 **접합 차단 조건**이며, 차단 전엔 진열 금지.
   추가로 블록 엔티티 상태가 **결정론 조성(같은 입력=같은 마을)**에 새 계층을 더한다.

### 6.2 결정적 사실 — **Java 25는 26.x의 이득이 아니다** (실측)

1차 조사는 "Java 25 = 26.x의 비용"으로 적었다. 프레이밍이 틀렸다. 진짜 질문은
**"Java 25를 쓰려면 26.x로 가야 하는가?"**이고, 답은 **아니다**.

**Paper 1.21.11(build 132)을 JDK 25로 실제 부팅했다:**

```text
[bootstrap] Running Java 25 (OpenJDK 64-Bit Server VM 25.0.3+9-LTS; Temurin) on Linux (aarch64)
[INFO]: Starting minecraft server version 1.21.11
[INFO]: This server is running Paper version 1.21.11-132 (STABLE)
[INFO]: Done (14.054s)! For help, type "help"
```

`-XX:+UseZGC`로 정상 기동. **경고도, 거부도 없다.**

> **따라서: 1.21.11 + Java 25 + 세대별 ZGC 조합이 지금 당장 가능하다.**
> Java 25가 주는 모든 것(GC·JIT·시동)은 **26.x로 가지 않고도 100% 취할 수 있다.**
> 이로써 **26.x의 마지막 기술적 명분이 소멸한다.** 26.x의 Java 25는 *이득*이 아니라 **입장료**다.

(Paper 문서 표는 1.21.x에 "Java 21 권장"이라 적지만, 이는 *최소·권장*이지 *상한*이 아니다. 실측이 이를 확인했다.)

### 6.3 Java 25 GC가 우리 블록 워크로드에 주는 것 — **측정했다. 0이다.**

**GC 사실관계부터 바로잡는다:** 세대별 ZGC는 **Java 21에도 이미 있다.** Java 21에선 `-XX:+ZGenerational`
플래그로 켜고, Java 25에선 그것이 **기본값**이 된 것이다. 즉 **"세대별 ZGC"는 Java 25의 신기능이 아니라
Java 21의 기본값 변경이다.** ([OpenJDK ZGC Wiki](https://wiki.openjdk.org/spaces/zgc/pages/34668579/Main))
→ 우리는 **JDK 21에서 플래그 한 줄로 이미 그 이득을 취할 수 있었다.**

**청크 생성 벤치마크 (동일 jar · 동일 시드 · 동일 GC · 3회 반복):**

```text
Paper 1.21.11-132 · seed=honcheon1234 · level-type=normal · -Xms4G -Xmx4G
-XX:+UseZGC -XX:+ZGenerational  (양쪽 모두 세대별 ZGC — 사과 대 사과)

"Prepared spawn area" (= 순수 지형 생성 시간)
  JDK 21 :  5891 / 5905 / 6073 ms   → 평균 5,956 ms
  JDK 25 :  6047 / 6295 / 6033 ms   → 평균 6,125 ms

  차이: JDK 25가 2.8% **느리다** — 노이즈 범위. 이득 없음.
```

**결론: Java 25는 우리 청크 생성을 빠르게 하지 않는다.** 측정 가능한 이득이 **0**이다.

**왜 그런가 — 우리 워크로드의 성질 때문이다:**

| 우리가 하는 일 | GC 개선이 돕는가 | 이유 |
|---|---|---|
| **청크 생성** | **아니다 (실측)** | 위 벤치마크. 지형 생성은 CPU 연산 바운드지 GC 바운드가 아니다 |
| **대량 `setType`/`getBlockAt`** (조성기·검수·조감) | **아니다** | 이건 **한 틱 안의 동기 스톨**이다. GC 일시정지를 1ms로 줄여도 **900ms짜리 메인 스레드 정지는 그대로다.** GC는 여기 없다 |
| **엔티티 티킹** (스포너·전의) | **아니다** | 상시 부하가 애초에 없다 — 존당 10초에 몹 1마리, 존 상한 18, 96블록 내 플레이어 없으면 조기 반환 |
| **파티클 발행** (오의·격) | **아니다** | `spawnParticle` 호출부가 **모듈 전체에 3곳**이고 전부 예산 상한이 걸려 있다 |
| **할당 압력 전반** | **아니다** | 틱당 할당 폭풍이 **없다.** 가장 무거운 게 `getNearbyEntities()` 리스트 하나다 |

> **정직한 한 줄: 우리 워크로드는 GC 바운드가 아니다.** 그래서 GC를 아무리 개선해도 얻을 게 없다.
> ZGC의 진가는 **큰 힙 + 높은 할당률 + 지연 민감**일 때 나온다. 우리는 셋 다 아니다
> (화이트리스트 4명, MVT 규모).

**벡터 API·가상 스레드·Project Leyden은?**
- **가상 스레드**: 코드에 **0건**. 게다가 **Bukkit API는 비메인 스레드에서 호출 금지**(`performance.yml: bukkit_api_from_async: 금지`)라
  **우리 블록 워크로드에는 원천적으로 못 쓴다.** 무관.
- **벡터 API**: 우리 코드에 SIMD로 이득 볼 수치 루프가 없다. 블록 API 호출은 벡터화 대상이 아니다. 무관.
- **Project Leyden(시동 시간)**: 서버 시동은 하루 1회다. **이득이 있어도 무의미하다.**

| 월드 마이그레이션 버그 | — | **해소됨.** Paper [#13740](https://github.com/PaperMC/Paper/issues/13740)·[#13749](https://github.com/PaperMC/Paper/issues/13749) **둘 다 CLOSED**(2026-04) |

**정정: "26.1은 마이그레이션 버그가 있다"는 1차 조사의 반대 근거는 이제 유효하지 않다.**

### 6.5 진짜 병목은 버전이 아니다 — **`CheonghaBuilder`다** (본 조사 최대 수확)

성능을 조사하라는 지시를 받고 **우리 코드를 실측한 결과**, 버전보다 훨씬 큰 것이 나왔다.

**과제가 전제한 것과 실제:**

| 전제 | 실측 | 판정 |
|---|---|---|
| "세계가 1:1이라 **청크 생성이 병목**이다" | `world_map.yml:1563` `build_plan.now` = **`cheongha_hyeon` 하나뿐.** 원거리 지역은 **좌표만 등록**돼 있고 `build: later/never`. `disk_budget`은 **~484청크 / 10~25MB**로 잡혀 있다. 원거리 청크 생성 경로(`WorldMap.scoreSeed`)는 **호출부가 아예 없다(死코드)** | ❌ **병목 아니다.** 큰 좌표는 YAML 속 정수일 뿐 — **비용이 0이다** |
| "스포너·전의 티커가 상시 돈다" | 반복 태스크 **3개뿐**. `SkillListener`는 HUD를 **4틱마다**로 자체 스로틀(`tick % 4 != 0 → return`), `HuntingGrounds`는 **1Hz + 96블록 내 플레이어 없으면 조기 반환** + 존당 **10초에 몹 1마리** + 상한 18 | ❌ **가볍다.** 잘 설계돼 있다 |
| "파티클 예산이 등록돼 있다" | `spawnParticle` 호출부가 **모듈 전체에 3곳.** `SkillHud`만이 실질 발행처이고 **이미 예산·LOD 상한이 걸려 있다** | ❌ **문제 없다** |
| "조성기가 무겁다" | **✅ 사실이고, 생각보다 훨씬 심각하다 (아래)** | ✅ **여기가 병목이다** |

**`CheonghaBuilder`는 한 틱 안에서 동기 블록 API를 ~75만~95만 회 호출한다.**

```java
// CheonghaBuilder.java:381  clearAndFlatten — 단일 메서드가 지배적이다
for (int x = cx - 62; x <= cx + 62; x++)          // 125
    for (int z = cz - 62; z <= cz + 62; z++) {   // 125  → 15,625 columns
        world.getBlockAt(x, cy, z).setType(Material.GRASS_BLOCK);
        for (int y = cy + 1; y <= cy + 18; y++)  //  18
            world.getBlockAt(x, y, z).setType(Material.AIR);
    }
// → 296,875 setType + 296,875 getBlockAt = 이 메서드 하나로 593,750 호출
```

| 작업 | 규모 (실측) |
|---|---|
| `CheonghaBuilder` 1회 조성 (`/혼천 조성`) | **~35만~42만 write + ~40만~55만 read ≈ 75만~95만 동기 호출** |
| `TownAudit` (`/혼천 검수`) | `scanVolume` 131×131×22 = **377,542** + 나머지 → **~50만~54만 read** |
| `TownRender` (`/혼천 조감`) | 131×131 컬럼 × ≤31 y → **~41만~53만 read** |

**그리고 배치가 전혀 없다.** `CheonghaBuilder.java` 전체에서
`BukkitRunnable`·`runTaskLater`·`runTaskTimer`·`getScheduler`·`CompletableFuture` **히트 0건**.
유일한 스케줄링 관련 호출은 `CheonghaBuilder.java:399`의
`world.getChunkAt(chunkX, chunkZ).load(true)` — **동기 강제 청크 로드**로, 상황을 **악화**시킨다.
`ChunkSnapshot` 사용도 `TownAudit`·`TownRender` 양쪽 **0건**이다.

> **이것은 `performance_and_netcode.md:14-16`이 스스로 지목한 3번 랙 유형
> — "동기 I/O가 메인 스레드를 세움 (스파이크형 멈춤)" — 그 자체다.**

**핵심: 어떤 마인크래프트 버전도, 어떤 JDK도 이걸 고쳐 주지 않는다.**
GC 일시정지를 10ms → 0.5ms로 줄여도, **한 틱에 90만 번 동기 호출하는 메인 스레드 정지**는 그대로다.
고치는 방법은 버전이 아니라 **틱 분할 배치 + 물리 억제(`setBlockData(..., false)`) + 스냅샷 읽기**다.

**따라서 "성능을 원한다"는 요구의 정답은 26.x가 아니라 `CheonghaBuilder` 배치화다.**
그리고 그건 **1.21.4에서도, 1.21.11에서도 지금 당장 할 수 있다.**

### 6.6 계측이 없다 — 이것이 가장 정직한 결론이다

`grep`으로 확인: 코드 전체에 **MSPT·TPS·spark·나노타임 프로파일링이 0건**이다.
`performance_and_netcode.md:80`이 *"상시 계측: spark/MSPT 프로파일링 상시 가동"*을 요구하지만 **미구현**이고,
`config/performance.yml`의 예산(`server_target_mspt: 40`)은 **희망이지 측정값이 아니다.**

> **베이스라인이 없으므로, "버전을 올리면 빨라진다"는 주장은 현재 반증 불가능하다.**
> 유일한 예외: `TownRender.java:546`이 스스로 블록 읽기 횟수와 ms를 로그로 찍는다.
> **`/혼천 조감`을 한 번 돌리면 실제 수치가 나온다 — 가장 싼 측정이다.**

### 6.7 판정

**성능·기술을 포함해도 답은 1.21.11이다. 그리고 이번엔 근거가 실측이다.**

```text
26.x가 성능·기술로 주는 것:
  청크 생성 개선      0   (26.1은 포맷을 안 건드렸다 — 위키 전수 확인)
  서버 틱 개선        0   (26.2의 Vulkan은 클라 전용)
  청크 시스템 재작성  0   (Moonrise는 이미 1.21.4의 Paper에 들어 있다)
  remapper 폐지 이득  0   (우리는 NMS 0건)
  Java 25 GC 이득     0   (실측: 청크 생성 2.8% 느림 = 노이즈. 우린 GC 바운드가 아니다)
  데이터 주도 거래    잠재적 (그러나 TradeListener로 이미 자체 구현)
  ──────────────────────
  합계                ≈ 0

26.x가 요구하는 것:
  JDK 25 설치 + Gradle 8→9 메이저 업그레이드 (실측: 8.12는 JDK25에서 BUILD FAILED)
  전 모듈 Java 타깃 정합 (17/21 혼재 → 25)
  플레이어 4명 전원 26.1 클라 (생태계 미성숙)
  빌드 핀 고정 좌표 관리
```

**이득 ≈ 0 · 비용 > 0 이므로, 성능·기술 축을 포함해도 26.x는 정당화되지 않는다.**
1차 결론과 같은 곳에 도착했지만 **길이 다르다** — 1차는 "비용이 크다"(틀렸다)였고,
2차는 **"이득이 없다"**(실측)이다.

**단계적 경로 — 가능하고, 이것을 권한다:**

```text
1.21.11 (Java 21 · Gradle 8.12 그대로 — 코드 6줄)
   ↓ [선택] Java 25 로 런타임만 교체 — 실측상 이득은 없지만, 원한다면 지금도 가능하다
   ↓        (JDK 25 설치만. 코드·Gradle·플러그인 변경 0. 되돌리기도 자유)
   ↓ [진짜 성능 작업] CheonghaBuilder 배치화 — 버전과 무관. 이게 유일하게 효과가 있다
   ↓
26.1 재평가 (M3 이후)
```

**26.1로 바로 갈 이유는 없다.** 다만 1차 조사가 말한 "26.x는 위험하다"도 이제는 과장이다 —
**26.1.2는 STABLE이고 마이그레이션 버그도 닫혔다.** 26.x는 **위험해서 안 가는 게 아니라, 갈 이유가 없어서 안 간다.**

**재평가 시점:**
1. **26.3 출시 후** (Q3 2026 예정) — 그때 블록 추가분을 다시 센다
2. **Gradle 9 + JDK 25로 이미 이주해야 할 다른 이유가 생겼을 때** — 그러면 26.x의 툴체인 비용이 0이 된다
3. **26.2가 STABLE이 되고 진사(cinnabar = 朱砂)를 쓰기로 결정했을 때** — 그건 성능이 아니라 **블록 사유**다
4. **동시 접속이 4명 → 수십 명으로 늘 때** — 그때 비로소 GC·틱이 실제 변수가 된다. **지금은 아니다**

### 7.1 2차 조사(성능·기술)에서 확인하지 못한 것

7. **"26.1이 엔티티 처리를 병렬화했다"는 주장을 확인하지 못했다.** 일부 호스팅 블로그가 주장하지만
   **minecraft.wiki 26.1 기술 변경란에 근거가 없고**, Folia(리전 스레딩) 설명과 뒤섞인 SEO 문서로 보인다.
   1차 출처를 못 찾았다. **"모른다"로 남긴다.** 만약 사실이라면 26.x 평가가 바뀔 수 있다 —
   다만 우리는 **엔티티 부하 자체가 거의 없어서**(§6.5) 사실이어도 이득은 작을 것이다.
8. **우리 플러그인을 26.1.2 런타임에서 실제로 돌려 보지 못했다.** 컴파일은 통과했지만
   **런타임 동작(조성·검수·조감 전 경로)은 검증 못 했다. 컴파일 통과 ≠ 동작 보장.**
9. **`CheonghaBuilder` 조성의 실제 벽시계 시간을 측정하지 못했다.** 75만~95만 호출은 **정적 분석(루프 경계)**
   에서 나온 수이고, 실제 MSPT 스톨은 **서버에서 `/혼천 조성`을 돌려야** 나온다.
   → **가장 싼 실측: `/혼천 조감` 1회.** `TownRender.java:546`이 블록 읽기 횟수와 ms를 스스로 로그에 찍는다.
10. **Java 21 vs 25 벤치마크는 청크 생성 한 축만 쟀다.** 대량 `setType` 쓰기·엔티티 티킹을
   JDK별로 비교하지 못했다(플러그인 런타임 미가동). 다만 **그 워크로드들은 GC 바운드가 아니므로**(§6.3)
   결과가 뒤집힐 가능성은 낮다고 **본다**. — 낮다고 "본다"이지, **쟀다는 뜻이 아니다.**
11. **벤치마크 조건이 좁다: aarch64 1대 · 힙 4G · 3회 반복.** x86_64나 더 큰 힙(16G+)에선 다를 수 있다.
   특히 **ZGC의 이점은 힙이 클수록 커진다** — 우리가 4G로 쟀다는 점을 명시해 둔다.
   (다만 우리 실사용은 화이트리스트 4명 규모라 4G가 오히려 현실적이다.)
12. **26.x 클라이언트 생태계 성숙도를 조사하지 않았다** (최적화 모드·리소스팩 도구의 26.x 지원 현황).
   플레이어 4명이 26.1 클라를 써야 하므로, 26.x行을 재검토할 땐 이걸 먼저 봐야 한다.

## 8. 가구·표현력 축 — 3차 조사

### 8.3 ② 몹 오브젝트·엔티티 표현력 — **사용자가 짚은 축은 맞고, 버전은 틀렸다**

### 8.4 ③ 판단 — 무엇이 유지되고 무엇이 뒤집히는가

**유지된다 — 지금의 목적지는 1.21.11이다.** 가구 축을 넣어도 26.1·26.2로 갈 이유는 **여전히 0**이다:

```text
26.1 : 가구 0 · 성능 0 · 표현력 0   +  JDK 25 · Gradle 8→9 비용   → 순손실
26.2 : 가구 0 · 성능 0 · 표현력 0   +  위 전부 + Paper ALPHA        → 순손실
```

**뒤집힌다 — 최종 목적지는 26.3이다.** 2차 조사의 *"26.x는 갈 이유가 없다"*는 **26.3에 대해 틀렸다.**
§6.7이 스스로 건 재평가 조건 ①**"26.3 출시 후 블록 추가분을 다시 센다"**가 **발동했고, 세어 보니 가구가 있다.**

**"26.3의 가구만으로 JDK 25 + Gradle 9 비용을 감수할 만한가?" — 수치로 답한다:**

| 얻는 것 (26.3) | 개수 | 무엇이 무엇으로 |
|---|---|---|
| 앉을 수 있는 좌석 | **객잔 걸상 12 + 교의 1 + 의방·의뢰소·쉼터·표국 다수 ≈ 20~25석** | `SPRUCE_STAIRS`(앉기 불가) → **계단 + `cushion`**(실제 착석) |
| 등급별 방석 색 | **16색** | `BROWN_CARPET` 단색 4곳 → 부촌 적·자 / 빈촌 갈·회 (`village_tiers` 실내 축 성립) |
| 짚 침상 | 객잔 봉놋방 · 빈촌 민가 | **없음** → `straw_bed` (스폰 이동 없음 = 부작용 0) |
| 좌식 단 | 양털 계단·반블록 16색 | `BROWN_CARPET` → 흡음 좌식 단 |
| 목재 팔레트 | 포플러 1종(+`poplar_shelf`) | — |
| **총 비용** | **JDK 25 + Gradle 8→9 + 팩 `pack_format` 110.0** | **1.21.11行에서 이미 팩을 갈아엎으므로 팩 재작업은 중복 아님** |

**판정: 감수할 만하다 — 단, 26.3이 나온 뒤에.** 근거:
1. **툴체인 비용은 어차피 한 번은 치른다.** JDK 25 + Gradle 9는 26.x行의 **입장료**이고, 26.3에 가려면 **반드시** 낸다.
   26.1에 낼 땐 **얻는 게 0이라 순손실**이었지만, 26.3에 내면 **좌석 20~25석 + 침상 + 16색 등급 축**을 얻는다.
   **같은 비용, 처음으로 대가가 있다.**
2. **가구는 팩으로 대체 불가능하다.** 기와·회벽은 텍스처로 흉내 낼 수 있지만 **"앉는다"는 기능이라 텍스처로 못 만든다.**
   방석은 **리소스팩이 절대 줄 수 없는 것**을 준다. 이것이 사용자가 말한 **"기능적 측면"**의 정확한 값이다.
3. **수묵 리스크가 0이다.** 구리와 달리 방석은 **무채색을 고르면 끝**이다 — 검수 룰 개정도, 팩 재텍스처도 불필요.

**그러나 지금 26.3으로 갈 수는 없다 — 미출시다.**

```text
26.3 스냅샷 3 = 2026-07-07 (닷새 전)   ← 방석·짚 침상이 여기 들어왔다
26.3 정식     = Q3 2026 예정 · 미출시
Paper 26.3    = 존재하지 않는다
```

**따라서 2단 이주가 답이다:**

```text
[지금]  1.21.11  — 코드 6줄. 시렁(*_shelf, 도난 잠금 포함) · 창살 · 등롱 · 창(槍) · mannequin 수확
                   Java 21 · Gradle 8.12 유지 = 툴체인 비용 0
   ↓    26.1 · 26.2 는 **건너뛴다** (가구 0 · 성능 0 — 들를 이유가 없다)
   ↓
[26.3 출시 후]  26.3 — 가구 수확. 이때 JDK 25 + Gradle 9 비용을 **처음으로 대가를 받고** 지불한다
                   방석 → 걸상·교의·평상 / 짚 침상 → 객잔·빈촌 / 양털 16색 → 등급 축
```

**26.3 이주 선결 조건(그때 확인할 것):**
1. Paper 26.3 **STABLE** (26.2는 릴리스 한 달 뒤에도 ALPHA였다 — §1.0. 26.3도 서두르지 않는다)
2. **방석 = 엔티티**라는 사실의 대가를 측정 — §8.5
3. 스냅샷 사양이 정식 출시까지 **유지되는지** (스냅샷은 바뀔 수 있다)

### 8.5 26.3의 숨은 비용 — **방석은 블록이 아니라 엔티티다**

이것이 가장 중요한 각주다. `cushion`은 **블록이 아니라 엔티티**다. 결과:

| 항목 | 영향 |
|---|---|
| **`TownAudit` 소품 예산** | **한 점도 안 쓴다.** 블록 스캔에 안 잡힌다 — 계단 걸상이 "PROP 집합 밖이라 예산 0"이었던 것과 **같은 이유로** 무료 (`CheonghaBuilder:214`) |
| **`CheonghaBuilder` 결정론** | ⚠️ **새 부담.** 방석은 `setType`이 아니라 **`spawnEntity`**다. 재조성 시 **기존 방석을 지우지 않으면 중복 생성**된다. "같은 입력 = 같은 마을" 보장에 **엔티티 정리 경로가 새로 필요**하다 |
| **엔티티 부하** | 마을 전역 **20~25개 상주 엔티티** 추가. AI가 없어 틱 비용은 낮지만 **0은 아니다** |
| **`mob_spawning.md` 스폰 게이트** | `SpawnReason` 필터가 **`CUSTOM`을 통과**시키므로 방석 소환은 막히지 않는다 — 확인 필요 항목 |
| 지지 블록 의존 | 아래 블록이 사라지면 **방석이 파괴된다.** 마을 개축 시 유의 |
| 자연 생성 | **버려진 캠프에 16색 전부 생성.** 우리는 방석을 **징발이 아니라 용도 그대로** 쓰므로 **무해** |

> **정직: 방석의 이득은 크지만 공짜가 아니다.** 블록이었다면 결정론 비용이 0이었을 텐데, 엔티티라서
> `CheonghaBuilder`에 **엔티티 생명주기 관리**가 처음으로 들어온다. 이것은 §6.5의 배치화 작업과 함께 설계돼야 한다.

### 8.6 3차 조사에서 확인하지 못한 것 (정직하게)

13. **26.3은 스냅샷이다 — 사양이 바뀔 수 있다.** 방석의 제작법·색·충돌 판정은 **2026-07-07 스냅샷 3 기준**이다.
    정식 출시(Q3 2026)까지 **변경될 수 있고, 최악의 경우 잘려 나갈 수도 있다.** 스냅샷을 근거로 이주를 확정하면 안 된다.
    → **본 문서는 "26.3이 나오면 간다"이지 "지금 26.3으로 간다"가 아니다.**
14. **26.3의 Java·Gradle 요구사항을 확인하지 못했다.** 26.1이 Java 25였으므로 26.3도 최소 25일 것으로 **추정**하나,
    **26.3 스냅샷을 실제로 컴파일해 보지 않았다.** (§6.4의 26.1.2 실측과 달리 이건 **추정이다.**)
15. **방석에 NPC를 앉힐 수 있는지 확인하지 못했다.** 문서는 **플레이어**의 착석만 말한다.
    객잔에 **손님 NPC가 앉아 있는** 그림이 되려면 이게 돼야 하는데, **모른다.** 26.3 출시 후 실측 항목.
16. **`mannequin`의 스킨 지정 방식을 완전히 확인하지 못했다.** `profile`이 **리소스팩 텍스처 경로**를 직접 받는지,
    아니면 **실제 플레이어 UUID/스킨 서버**를 요구하는지가 갈린다. 후자라면 오프라인 서버에서 제약이 생긴다.
    (위키는 `entity/player/wide/steve` 같은 **네임스페이스 ID** 예시를 보여 주지만, 커스텀 팩 텍스처 사용 가부는 **미확인**.)
    → **NPC 표현 전략을 갈아엎기 전에 반드시 실측할 것.**
17. **`equippable{asset_id}`를 실제로 적용해 보지 않았다.** 1.21.4에서 된다는 것은 **문헌 근거**이고,
    우리 팩·아이템 정의와의 접합은 **미검증**이다. 다만 **버전 이주와 무관하게 지금 검증할 수 있다.**
18. **탁자·병풍·발(簾)을 주는 버전이 정말 없는지** — 26.3 스냅샷 1~3 목록과 1.21.5~26.2를 훑었으나,
    **모든 스냅샷의 전체 변경 목록을 한 줄씩 대조하지는 않았다.** "없다"는 **누락 가능성이 있는 없다**이다.

* **선반(`*_SHELF`)** — 1.21.11 이 준 진짜 시렁. 벽에 붙어 **물건 셋을 얹는다**.
  * 표국 남벽: 진철산의 창(정련) + 표사의 도·검·월아산·단검 — 표국이 무엇으로 먹고사는 집인지 문턱에서 읽힌다.
    빈 칸 하나는 "지금 표행 나간 병기"다.
  * 의방 남벽: 약장 가운데 켜 위 약재 시렁 (말린 버섯·열매·해초)
  * 객잔 북벽: 계산대 뒤 술 시렁 — 블록으로 세운 단지 둘 대신 시렁 하나에 술 셋
  * 조성기 규약 준수: 개체 굴림 씨앗 = **좌표 해시**(`Math.floorMod(31*cx + cz, …)`) — 난수 금지
  * `TownAudit.PROP` 에 `*_SHELF` 12종 등록 — 시렁도 소품 예산(벽 한 면 3점)을 먹는다

### 이주가 드러낸 결함 (1.21.11 파괴적 변경)
* **`ItemMeta.setEnchantable(0)` 이 던진다** — "Enchantability must be positive".
  0 은 컴포넌트가 담을 수 없는 값이다. 마법부여를 끄는 법은 값을 0 으로 두는 게 아니라
  **컴포넌트를 지우는 것**(`setEnchantable(null)`)이다 — `minecraft:enchantable` 이 없는 아이템은
  마법부여대가 받지 않는다(1.21.2+ 규칙).
  이것은 **병기 제작 전체를 죽이고 있었다** (`Weapons.make` 의 마지막 줄) — 조성기가 시렁에 병기를
  얹기 시작하면서야 드러났다. 이주 검산이 코드만 컴파일해 보고 끝났다면 못 봤을 결함이다.
* **조성 중 시렁이 빈 채로 섰다** — 라이브 인벤토리에 곧장 넣으면 타일 엔티티가 아직 붙지 않아 조용히 사라진다.
  스냅샷 인벤토리에 담고 `update()` 로 되쓴다.
